## 0. 背景と決定事項

### 0.1 背景

- 2026-10-31 の GCP での障害の試験で、入口（浮動 IP）の台を止める場面の回復が 140〜227 秒かかった（中継なしでも 77〜88 秒）。原因は GCP の外部 IP の付け替えが「アクセス設定の削除 → 追加」の 2〜3 操作になる制約で、AWS の Elastic IP の付け替え（1 操作）より桁で遅い。
- 本番では利用者は VPC の内側から LiteLLM を呼ぶ（Zscaler は外向きの通信だけに関わる）。公開の入口はそもそも不要で、入口はプライベートで足りる。
- 本番のクラウドの権限は別部署が持ち、資源はすべて依頼して作ってもらう。**VM が実行時にクラウドの API を呼ぶ方式（keepalived ＋ IP の付け替え）は、VM に IAM の権限を付けてもらう依頼が残る**ので避けたい。
- 本番ではクラウド側のファイアウォールが無い前提に立ち、VM と k3s の中だけで守りたい。管理画面と DB への接続元は踏み台 1 台に絞りたい。
- 監視は組織の標準の Zabbix で行いたい。検証環境では Zabbix のサーバーも `./lab` が作る。

### 0.2 決定事項（2026-10-31、ユーザーの回答）

| # | 問い | 決定 |
|---|---|---|
| 1 | 入口の台を止める場面の回復時間（中継経由で 140〜227 秒）の扱い | 中継経由の計測値は受け入れ、中継なしの再計測はしない（本番は AWS で、計測する意味が薄い） |
| 2 | k3s の版上げの切断時間 | 実測したい（「一番知りたい」）。入口でない台から上げ、入口を先に移してから上げる |
| 3 | 入口を公開 IP からプライベート IP に変える | **変える**（A）。本番は内側から呼ぶため |
| 4 | Mac 上のクライアント（Claude Code、Codex）の接続経路 | **SSH の転送経由**（A）。転送だけを張る命令を足す |
| 5 | AWS の 3 台の置き方と IP の付け替え方式 | 同一サブネット ＋ API で付け替え（A）と答えた後、**内部ロードバランサに変更**（次項） |
| 6 | IP の付け替え（API）か内部ロードバランサか | **内部ロードバランサ**（A）。AWS は内部 NLB、GCP は内部パススルー ネットワーク ロードバランサ。keepalived と VM のクラウド権限を無くす。AWS の 3 台は別 AZ のまま |
| 7 | 本番の踏み台 | **別部署が用意する踏み台 1 台の IP（CIDR）を `.env` に書く**（A）。検証では中継（Zscaler 役）の VM がその役 |
| 8 | 監視をこの変更に含めるか | **含める**（B）。Zabbix agent 2 と Kubernetes の監視まで。**Zabbix のサーバーも `./lab` が自動で作る**（追加の指示） |

### 0.3 既存の仕様から変える方針

- **入口**: 公開の浮動 IP（Elastic IP／静的な外部 IP）と keepalived を廃止し、内部ロードバランサ（L4、TCP の素通し）の内部 IP を入口にする。TLS は今までどおり Traefik が終端し、Let's Encrypt（DNS-01）もそのまま。
- **VM のクラウド権限**: 廃止。VM はクラウドの API を呼ばない（GCP のノード用サービスアカウント、AWS のインスタンスプロファイル、`vm/hooks-*.sh`、起動時に外向き IP を戻すサービスを消す）。
- **守り**: クラウドのファイアウォールに頼らず、各 VM の nftables、Traefik の経路ごとの送信元制限、Kubernetes の NetworkPolicy の 3 層で守る。managed（検証）ではクラウドのファイアウォールは「通すため」だけに最小限作る。
- **操作者（Mac）の経路**: SSH は各台の固定の公開 IP へ（今までどおり）。HTTPS は踏み台（検証では中継の VM）を経由する SSH のポート転送でロードバランサの内部 IP へ届く。Mac 用の別名（`LAB_LOCAL_HOSTNAME`）を証明書に足す。
- **監視**: Zabbix agent 2 を全 VM に、Zabbix の公式 Helm チャート（zabbix-proxy、agent の DaemonSet、kube-state-metrics）をクラスタに入れる。検証環境では Zabbix のサーバーを踏み台の VM で動かす。本番では既存の Zabbix サーバーの宛先を `.env` に書く。ホストとテンプレートの登録は Zabbix の API で `./lab` が行う。

## 2. 要件

### 2.1 入口（内部ロードバランサ）

- R1. 入口は内部ロードバランサの固定の内部 IP。80 と 443 を 3 台の Traefik（k3s の ServiceLB が各台で受ける）へ TCP のまま流す。送信元 IP を保つ。
- R2. ヘルスチェックは TCP 80。間隔と失敗回数は、AWS は 10 秒 × 2、GCP は 5 秒 × 2。
- R3. managed では `./lab` がロードバランサ（AWS: 内部 NLB ＋ ターゲットグループ 2 つ、GCP: 静的内部 IP ＋ ヘルスチェック ＋ バックエンドサービス ＋ 非マネージドインスタンスグループ 3 つ ＋ 転送ルール）を作り、識別子と IP を `.env` に書く。provided では用意する側が作り、`.env` の識別子から IP を引く。
- R4. ホスト名の A レコード（Cloudflare、DNS のみ）はロードバランサの内部 IP を指す。証明書は Let's Encrypt の DNS-01（今までどおり）。
- R5. 公開の浮動 IP、keepalived、`vm/hooks-*.sh`、`lab-take-entry-ip.sh`、`lab-egress.service`、GCP のノード用サービスアカウント、AWS のインスタンスプロファイルを廃止する。VM はクラウドの API を呼ばない。
- R6. AWS の 3 台は別 AZ のまま（NLB のクロスゾーンを有効にする）。

### 2.2 VM 側の防御（クラウドのファイアウォール無しでも守る）

- R7. 各 VM の nftables で、入りは次だけ許し、ほかは拒む: 22 は踏み台（managed では操作者の IP も）から、80/443 は VPC の CIDR とロードバランサのヘルスチェックの送信元から、k3s の内部通信（6443、2379-2380、10250、8472/udp、30500）は 3 台の固定 IP から、Zabbix agent（10050）は Zabbix サーバー（と zabbix-proxy の Pod 網）から、Pod 網（cni0、flannel.1）は無条件。
- R8. 各 VM の nftables で、出は次だけ許し、ほかのインターネットは拒む: 3 台、ロードバランサ、踏み台（中継 3128、Zabbix 10051）、メタデータサーバーと DNS・NTP（クラウドの内部アドレス）、確立済みの応答。Pod からの転送も同じ規則。GCP の外向き遮断のファイアウォールは廃止し、この規則で代える。
- R9. Traefik の経路のうち管理系（`/ui`、`/login`、`/sso`、`/lab-audit`、`/metrics`）は踏み台からだけ通す（`IPAllowList`）。利用者の API（`/v1`、`/mcp`、`/health*`）は VPC の CIDR から通す。
- R10. PostgreSQL（Pooler を含む）と Valkey への接続は NetworkPolicy で、必要な Pod（LiteLLM、監査アプリ、CloudNativePG のオペレーターと Barman、Sentinel）に限る。クラスタの外への口（NodePort）は開けない。管理者の DB 接続は踏み台から SSH で入り `kubectl port-forward` で行う。
- R11. provided では、クラウドのファイアウォールが無くても上の 3 層で同じ守りになる。managed では、クラウドのファイアウォール（GCP は既定で入りを全部拒むので）に「通す」規則だけを作る（22、80/443、内部、ヘルスチェックの送信元、Zabbix）。

### 2.3 操作者（Mac）の経路

- R12. SSH は各台の固定の公開 IP（今までどおり）。managed では操作者の IP を 22 の許可に自動で入れる。
- R13. HTTPS は踏み台に SSH し、ロードバランサの内部 IP の 443 へポート転送（既定 127.0.0.1:18443）。`./lab` の全段階と試験、`./lab clients` が書くクライアントの設定はこの転送口を使う。転送だけを張る `./lab forward` を足す。
- R14. Mac 用の別名 `LAB_LOCAL_HOSTNAME`（例 `lab-local.<ドメイン>`）の A レコードを 127.0.0.1 で作り、証明書の SAN に足す。Mac はこの名前と転送口のポートで接続する（証明書の検証が通る。`/etc/hosts` に触らない）。
- R15. 検索アプリ（監査ログの閲覧）の `BASE_URL` は、`LAB_LOCAL_HOSTNAME` があればその別名と転送口のポート、無ければ本番のホスト名。Google の OAuth クライアントのリダイレクト先は利用者が登録する（今までどおり）。

### 2.4 Zabbix

- R16. 全 VM（3 台と踏み台）に Zabbix agent 2 を入れ、能動（active）で Zabbix サーバーへ送る。ホスト名は VM の名前。
- R17. クラスタに Zabbix の公式 Helm チャート（zabbix-proxy、agent 2 の DaemonSet、kube-state-metrics）を入れ、テンプレート「Kubernetes cluster state by HTTP」「Kubernetes nodes by HTTP」「Kubernetes kubelet by HTTP」で k3s を監視する。
- R18. managed（検証）では、`./lab` が踏み台の VM で Zabbix サーバー（server ＋ web ＋ PostgreSQL、Docker Compose）を動かす（`LAB_ZABBIX_VM=true`）。provided では `.env` の `LAB_ZABBIX_SERVER`（既存サーバーの宛先）と `LAB_ZABBIX_API_URL`・`LAB_ZABBIX_API_TOKEN` を使う。
- R19. ホスト・ホストグループ・テンプレートの紐付け・zabbix-proxy の登録・Kubernetes のホスト（API の URL とトークン）・LiteLLM の入口の HTTP 監視（`/health/liveliness`）は、Zabbix の API で `./lab zabbix` が作る（冪等）。agent の自動登録のアクションも作る。
- R20. Zabbix の web 画面は踏み台経由の SSH の転送（既定 127.0.0.1:18080）で Mac から開く。
- R21. Zabbix を使わない環境（`LAB_ZABBIX_VM=false` かつ `LAB_ZABBIX_SERVER` 無し）では、agent も Helm チャートも入れず、段階は飛ばす。

### 2.5 障害の試験と版上げ

- R22. 障害の試験の `entry-node` は「Traefik の Pod が載った台を止める」場面に変える（ロードバランサがその台を外し、Traefik が別の台に移るまで）。目安は両クラウド 60 秒。
- R23. k3s の版上げは Traefik の台を最後にする（入口の移動を 1 回にする）。GCP で `./lab upgrade-k8s <次のマイナー版> --measure` を流し、要求の失敗の数と幅を記録する。

## 4. リスク・注意事項

- **nftables と k3s の共存**: kube-proxy と flannel が iptables（nf_tables 後端）に規則を書く。こちらの表は「入りの既定を拒否、Pod 網は許可」に留め、Kubernetes の鎖を壊さない。配備で Pod 間通信・ServiceLB・ClusterIP・NodePort を確かめる。
- **ヘルスチェックの送信元**: GCP は 35.191.0.0/16 と 130.211.0.0/22、AWS は VPC の中（NLB のアドレス）。nftables とクラウドのファイアウォール（managed）の両方に要る。
- **送信元 IP の保持**: GCP の内部パススルー LB と AWS NLB（インスタンスのターゲット）は送信元を保つ。Traefik の `IPAllowList` はこれに依存する。踏み台経由の SSH の転送は、送信元が踏み台の内部 IP になる。
- **Mac 用の別名の A レコード（127.0.0.1）**: Cloudflare が受け付けるかは配備で確かめる。受け付けなければ `/etc/hosts` の 1 行（利用者が足す）に切り替える。
- **GCP のエイリアス IP や外部 IP は使わない**ので、台を止めて起こしたときの公開 IP の入れ替わりは、managed の一時的な外部 IP（SSH 用）だけに残る。`refresh_public_ips` は維持する。
- **Zabbix サーバーの容量**: 踏み台の VM は e2-small（2 GiB）では足りないので e2-medium（4 GiB）、AWS は t3.medium にする。
- **LiteLLM の `/metrics`**: 公式文書が Enterprise の機能と表示している。今回は入口の HTTP 監視と Kubernetes のテンプレートに留め、LiteLLM と PostgreSQL の内部指標はバックログ。
- **本物の踏み台・Zabbix サーバー**は未確認。provided の試験は managed が作った資源で行う。

## 5. 用語

| 用語 | 意味 |
|---|---|
| 内部ロードバランサ | VPC の内側の IP で受け、後ろの VM に TCP のまま流す L4 のロードバランサ。AWS は内部 NLB、GCP は内部パススルー ネットワーク ロードバランサ |
| 踏み台 | 管理系の経路（管理画面、DB、Zabbix の画面）への唯一の入口となるホスト。検証では中継（Zscaler 役）の VM |
| 入口 | 利用者が接続する IP とホスト名。この変更後はロードバランサの内部 IP |
| 転送口 | Mac の 127.0.0.1 に開く SSH のポート転送の口（HTTPS 18443、Zabbix 18080、k3s 16443） |

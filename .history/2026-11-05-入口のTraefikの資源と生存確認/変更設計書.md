# 変更設計書: 入口の Traefik に CPU とメモリの要求を付け、生存確認を緩める

作成: 2026-11-05
状態: 実装済み・AWS で確認済み（3 章）・docs/ に反映済み（2026-11-05）
この文書の役割: **どう作るか**。要件と決定は `変更仕様書.md`

## 1. 設定（`k8s/traefik-config-vm.yaml`）

k3s に同梱の Traefik のチャートの値（HelmChartConfig の `valuesContent`）に足す:

- `resources.requests`: `cpu: 100m`、`memory: 64Mi`（上限は付けない）。BestEffort から Burstable になり、CPU が混んでも要求の分の取り分がある。
- `livenessProbe`: `timeoutSeconds: 5`、`failureThreshold: 6`（`periodSeconds` 10 と `initialDelaySeconds` 2 はチャートの既定のまま）。
  `readinessProbe` は変えない（応答しない台を送り先から早く外すため）。

台の CPU の要求の合計は 1 台あたり 0.1 コア増える。LiteLLM の最大数（`stages.litellm_max_replicas`）は台の空きから数え直すので、
足りなければ自動で減る。

## 2. 確認

- 配備した Traefik の Pod の定義に、要求と生存確認の値が入っていること。
- AWS で全 6 場面を、観測（台ごとの CPU の時系列を含む）付きの台本で流す。結果は 3 章。

## 3. 配備と試験の結果

2026-11-05 18:13〜19:10、AWS（`aws-ec2`、managed、負荷は中継の VM から）。構築から片付けまでを 1 本の台本で流した（19:10 に有料の資源 0 件）。
配備した Traefik の定義に `requests`（cpu 100m、memory 64Mi）と生存確認（時間切れ 5 秒、6 回）が入ったことを確かめた。

| 場面 | 今回 | 直す前（同じ測り方、16 時台） |
|---|---|---|
| pg-switchover | 失敗 0/1,222 件 | 0/1,205 件 |
| pg-pod | 失敗 0/1,210 件 | 1/1,209 件 |
| pg-node | **回復 90.9 秒**（失敗 1,147/5,370 件） | 175.1 秒（目安超過） |
| valkey-pod | 失敗 0/1,225 件 | 0/1,225 件 |
| valkey-node | **回復 83.6 秒**（失敗 1,383/5,126 件） | 159.7 秒（目安超過） |
| entry-node | **回復 66.3 秒**（失敗 870/5,875 件） | 100.8 秒 |

- 全 6 場面が目安以内。監査ログの欠けは全場面で 0 件。
- 止めていない台の Traefik が生存確認で再起動させられたことは無かった（直す前は 3 場面すべてで起きた）。
- 台ごとの CPU（10 秒ごと）: 台を止めた後、残りの 2 台は 1.6〜2.0 コア（割り当て可能な量の 105〜133%）に張り付いた。その間も Traefik は
  76〜114m の CPU を得ていた。直す前の Traefik の再起動は CPU の取り合いによるという推定を裏付ける。
- 止めた台に metrics-server（1 台だけ）が載っていると、その間は CPU の値が取れない（18:45〜18:46）。自動の台数調整も同じ値を使う。
- 残る停止は、入口と止めた台の Pod が外れるまで（約 40 秒）と、PostgreSQL の primary を失った場面での切り替えの間の 503（決定 3A で受け入れ）。

# 変更仕様書: Zabbix の監視の一揃い（VM・ノード・Pod・ディスク・DB・証明書・監査の整形）

作成: 2026-10-31
状態: 実装済み・GCP で配備と試験済み（2026-10-31。結果は変更設計書 4 章）。docs/spec.md 12.1、docs/design.md 21.11 に反映済み
この文書の役割: **何を満たすか（要件）と、何を決めたか（決定）**。どう作るかは `変更設計書.md`

## 0. 背景と決定事項

### 0.1 背景

`.history/2026-10-31-内部LBとVM側の防御とZabbix/` で入れた Zabbix は、VM の OS と Kubernetes の一部しか見ておらず、画面に
「Not available 1」「Unknown 18」「Average 1」が出ていた（2026-10-31 の確認）。原因は (1) 既定の「Zabbix server」ホストが自分のコンテナの中の
agent を聞いて失敗、(2) 能動 agent と HTTP だけのホストの受け身の枠が Unknown、(3) k3s のコントローラーとスケジューラーが 127.0.0.1 だけで
待ち受けて値が取れない、だった。ユーザーの指示: 「リソース、予定の Pod 数が足りなくなった、クラスタの台数が減った、VM と Pod のリソース、
ディスク容量など、必要な監視が一揃いできるようにして」。

### 0.2 決定事項（2026-10-31、ユーザーの回答）

| # | 問い | 決定 |
|---|---|---|
| 1 | 「Zabbix server」ホスト | 受け身の agent の OS のテンプレートを外し、Zabbix 自体の健全性だけ残す（A） |
| 2 | コントローラーとスケジューラー | k3s の待ち受けを開けて監視する（A） |
| 3 | 画面 | 専用のダッシュボードを `./lab zabbix` が作る（A） |
| 4 | 障害の知らせ | 検証では知らせない（画面だけ）。本番は既存の Zabbix サーバーの通知の設定に任せる（A） |
| 5 | 範囲 | 一覧の「足す」「直す」を全部（A） |
| 6 | 閾値 | 下の表の値（テンプレートの既定 ＋ 案）。`.env` では変えない（A） |

## 1. 要件（監視の一覧）

| # | 対象 | 見張ること | 閾値 |
|---|---|---|---|
| M1 | VM（3 台と踏み台） | CPU、メモリ、スワップ、負荷、ディスク、inode、読み取り専用化、ネットワーク、再起動、agent の途絶 | テンプレートの既定（CPU 90%、ディスク 80% 警告・90% 重大） |
| M2 | ノードの台数 | Ready のノードの数 | 3 未満で重大 |
| M3 | ノードの逼迫 | メモリ・ディスク・プロセスの圧迫があるノードの数、置けない（cordon）ノードの数、要求（requests）の合計と割り当て可能な量の比（CPU、メモリ） | 圧迫 1 台以上で警告、cordon が 30 分続いたら情報、要求が 90% を超えたら警告 |
| M4 | 予定の Pod 数 | Deployment・StatefulSet の数の食い違い（テンプレート）、Pending の Pod の数、LiteLLM の自動増減が上限に張り付き | Pending が 5 分続いたら警告、上限に 15 分張り付いたら警告 |
| M5 | Pod のリソース | コンテナごとのメモリと CPU の使用量と上限の比、OOM で落ちたコンテナの数 | メモリ 90% が 5 分で警告、CPU 90% が 15 分で警告、OOM 1 件以上で警告 |
| M6 | 制御部分 | API サーバー、kubelet、コントローラー、スケジューラー（テンプレート） | テンプレートの既定 |
| M7 | PostgreSQL | 動いている台数、状態、WAL の保管、最後のバックアップからの時間 | 3 未満で警告、状態が健全でないのが 10 分で警告、保管の失敗で重大、26 時間バックアップが無ければ重大（作って 26 時間以内は除く） |
| M8 | 入口 | `/health/liveliness` と `/health/readiness` | 3 分応答なしで重大（既存） |
| M9 | 証明書 | Let's Encrypt の証明書の期限と準備の状態 | 14 日未満で警告、準備できていないのが 1 時間で重大 |
| M10 | 監査ログの整形 | 整形の定期処理の最後の成功からの時間、失敗した Job の数 | 2 時間成功が無ければ重大、失敗 1 件以上で警告 |
| M11 | Zabbix 自身 | 既定の「Zabbix server」ホストは Zabbix の健全性だけ | |
| M12 | 画面 | ダッシュボード「litellm-lab」: 深刻度ごとの障害、障害の一覧、ノード数・Pending・PostgreSQL の台数・証明書の残り日数・要求の比の値、VM の CPU・メモリ・ディスクのグラフ | |

## 2. 検証項目

| # | 項目 | 合格 |
|---|---|---|
| V1 | `./lab up` の 2 回目 | Zabbix の設定・Helm・k3s の設定が変わらない（冪等） |
| V2 | 平常時 | 障害 0 件。コントローラー・スケジューラーのホストに値が入る。ダッシュボードが開く |
| V3 | 台を 1 台止める | 「Ready のノードが 3 未満」と止めた VM の agent の途絶が出て、起こすと消える |
| V4 | Pod が置けない | 大きな要求の Pod を作ると Pending の障害が出て、消すと消える |
| V5 | ディスク | 1 台のディスクを 85% まで埋めると「空きが少ない」が出て、消すと消える |
| V6 | OOM | 上限の小さい Pod でメモリを使い切ると OOM の障害が出る |

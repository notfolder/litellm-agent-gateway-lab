## 2. アイテム（ホスト `litellm-lab-k8s`。zabbix-proxy 経由）

kube-state-metrics の値は、テンプレートのスクリプトアイテム `kube.state.metrics` に従属させ、前処理「Prometheus のパターン」の集計（`function` の
`sum`）で 1 つの数にする。

| キー | 中身 |
|---|---|
| `lab.k8s.nodes.ready` | `kube_node_status_condition{condition="Ready",status="true"}` の合計 |
| `lab.k8s.nodes.pressure` | `kube_node_status_condition{condition=~"MemoryPressure|DiskPressure|PIDPressure",status="true"}` の合計 |
| `lab.k8s.nodes.unschedulable` | `kube_node_spec_unschedulable` の合計 |
| `lab.k8s.pods.pending` | `kube_pod_status_phase{phase="Pending"}` の合計 |
| `lab.k8s.containers.oomkilled` | `kube_pod_container_status_last_terminated_reason{reason="OOMKilled"}` の合計 |
| `lab.k8s.jobs.failed` | `kube_job_failed{namespace="litellm-lab",condition="true"}` の合計 |
| `lab.k8s.compactor.last_success` | `kube_cronjob_status_last_successful_time{namespace="litellm-lab",cronjob="audit-compactor"}` |
| `lab.k8s.cpu.requests` / `allocatable`、`lab.k8s.mem.requests` / `allocatable` | `kube_pod_container_resource_requests{resource="cpu|memory"}`、`kube_node_status_allocatable{resource=...}` の合計 |
| `lab.k8s.cpu.requests.pct` / `lab.k8s.mem.requests.pct` | 計算アイテム（要求 ÷ 割り当て可能 × 100） |
| `lab.k8s.hpa.litellm.current` / `max` | `kube_horizontalpodautoscaler_status_current_replicas` / `spec_max_replicas`（`horizontalpodautoscaler="litellm"`） |
| `lab.k8s.metrics.pods` | HTTP: `{$KUBE.API.URL}/apis/metrics.k8s.io/v1beta1/pods`（Bearer `{$KUBE.API.TOKEN}`、証明書の検証なし。履歴は残さない） |
| `lab.cnpg.cluster` / `lab.cnpg.backups` | HTTP: CloudNativePG の Cluster `litellm-pg` と Backup の一覧 |
| `lab.cnpg.ready_instances` / `instances` / `phase_ok` / `archiving` / `created` / `last_backup` | 上の 2 つに従属（JSONPath と JavaScript） |
| `lab.cert.litellm` → `lab.cert.not_after` / `ready`、計算 `lab.cert.days_left` | HTTP: cert-manager の Certificate `litellm-tls` |

発見ルール `lab.k8s.containers.discovery`（`lab.k8s.metrics.pods` に従属。名前空間・Pod・コンテナ）。プロトタイプ: メモリと CPU の使用量（Metrics API から
単位を換算）、上限（kube-state-metrics。無ければ -1）、計算アイテムの比（上限が無いコンテナは負になり発火しない）。失われた行は 1 時間で消す。

## 3. トリガー（すべて名前は「litellm-lab: 」で始める）

変更仕様書 1 章の閾値のとおり。式の例: `last(/litellm-lab-k8s/lab.k8s.nodes.ready)<3`、`min(/litellm-lab-k8s/lab.k8s.pods.pending,5m)>0`、
`now()-last(/litellm-lab-k8s/lab.cnpg.last_backup)>93600 and now()-last(/litellm-lab-k8s/lab.cnpg.created)>93600`。

## 4. 実装と試験で分かったこと（GCP、2026-10-31）

| # | 分かったこと | 対処 |
|---|---|---|
| 1 | Zabbix の Helm チャート 1.2.4 の `rbac.additionalRulesForClusterRole` は、テンプレートが追加分を字下げせずに埋め込み YAML が壊れる | 別の ClusterRole と ClusterRoleBinding を `./lab zabbix` が付ける |
| 2 | 「Kubernetes nodes by HTTP」テンプレートはノードごとにノード名のホストを作り、自動登録した VM のホスト（同じ名前）とぶつかる | 使わない。ノードの Ready・圧迫・cordon・要求の比は kube-state-metrics から自前のアイテムで数える |
| 3 | `kube_cronjob_status_last_successful_time` は一度も成功していない CronJob では出ない | 無ければ 0 にし、`kube_cronjob_created` と組み合わせて 2 時間を判定 |
| 4 | k3s の `config.yaml.d` の `+` 付きの鍵で、コントローラーとスケジューラーの引数を足せる。設定の変更による k3s の再起動は 1 台 12 秒ほどで、ノードは Ready のまま | 設計どおり |
| 5 | 別の台の zabbix-proxy からコントローラー（10257）とスケジューラー（10259）へは、Pod の外向きが台の IP に変わって届くので、nftables の 3 台の間の許可に要る | 設計どおり |

|---|---|
| 単体テスト | 103 本が通る |

| `./lab cluster` | 3 台の k3s に追加の設定が入り、1 台ずつ再起動。10257 / 10259 が全体で待ち受ける |
| 台を止める（node2、20:53〜21:02） | 1 分以内に「Ready のノードが 3 台未満」（重大）、PostgreSQL の台数不足、Valkey の StatefulSet の停止と食い違い |

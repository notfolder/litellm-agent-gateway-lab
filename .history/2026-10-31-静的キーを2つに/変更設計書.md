# 変更設計書: バケットの静的キー（IAM ユーザー）を 5 つから 2 つに

作成: 2026-10-31
状態: 実装済み・GCP で配備と試験済み（2026-10-31。4 章）。docs/spec.md 12.2、docs/design.md 21.5、docs/provider-requests.md に反映済み
対応する変更仕様書: 同じディレクトリの `変更仕様書.md`

## 1. 作り

論理の利用者（Mac の RustFS と同じ `litellm-writer` `audit-compactor` `audit-viewer` `pg-backup` ＋ `registry` ＋ `operator`）はコードの中に残し、
VM の環境では**鍵の役割**に写す。鍵の役割は 2 つ。

| 論理の利用者 | 鍵の役割（VM） |
|---|---|
| litellm-writer | `litellm-writer` |
| audit-compactor、audit-viewer、pg-backup、registry、operator | `lab-app` |

- `render.VM_KEY_ROLE_OF`（上の表）と `render.vm_key_role(user)`。`render.s3_env_names(user, env)` は VM の環境なら役割の名前で `.env` の項目を返す（`LAB_VM_S3_LAB_APP_KEY` など）。これで Secret の作成、Pod への配布、操作者のクライアント、監査の試験はコードを変えずに 2 つの鍵を使う。
- `clouds.static_key_policies(env)` に `operator` の論理の権限を足す（`cluster/*` の全操作、`audit-derived/*` の削除、バケットの設定の読み取り、一覧）。
- `clouds.s3_user_policies(env, bucket)` は役割ごとに論理の利用者の文を合併し（重複は除く）、拒否 2 文を付ける。
- `clouds.gcs_bindings(env, bucket)` も役割ごとに写す。操作者の無条件の objectAdmin は無くなり、`lab-app` に `cluster/` の objectAdmin、`audit-derived/` の objectUser、lister が付く。
- provision（`gcp.ensure_static_keys` / `aws_ec2.ensure_static_keys`）は役割 2 つを作る。GCP の `lab-app` は HMAC キーと JSON キー（registry の GCS ドライバ用）の両方。
- `destroy` は役割 2 つに加えて、前の版の名前（5 役割 ＋ operator ＋ node）も消す（`render.LEGACY_KEY_USERS`）。`ops.down` の `.env` の掃除も同じ。
- `vm.require_provided_env` は役割 2 つ（GCP は JSON キーも）を求める。
- `_set_bucket_iam`（GCP）の「管理するメンバー」は役割 2 つ ＋ 前の版の名前（残っていれば外す）。

## 2. `.env`

| 項目 | 意味 |
|---|---|
| `LAB_VM_S3_LITELLM_WRITER_KEY` / `_SECRET` | 原本を書く鍵 |
| `LAB_VM_S3_LAB_APP_KEY` / `_SECRET` | 監査アプリ・運用・操作者の鍵 |
| `LAB_VM_GCS_REGISTRY_KEY_JSON` | GCP の `lab-app` のサービスアカウントの JSON キー（registry 用） |
| 廃止 | `LAB_VM_S3_AUDIT_COMPACTOR_*`、`AUDIT_VIEWER_*`、`PG_BACKUP_*`、`REGISTRY_*`、`OPERATOR_*` |

## 3. 試験

単体テスト: `s3_env_names` の写し、`s3_user_policies` が 2 役割で拒否を含む、`lab-app` に `cluster/` と `images/` と `pg-backup/` の `s3:*` と `audit-derived/` の削除、`litellm-writer` は変わらない、`gcs_bindings` の役割、provided の要件の文言。
配備: 変更仕様書 2 章。

## 4. 実装と試験で分かったこと（GCP、2026-10-31）

| 試験 | 結果 |
|---|---|
| 単体テスト | 101 本が通る（鍵の写し、2 役割のポリシー、GCS のバインディング、provided の要件） |
| `./lab up`（managed、GCP） | 1 回目で全段階通過（16:21〜16:42）。サービスアカウントは `litellm-lab-litellm-writer` と `litellm-lab-lab-app` の 2 つだけ。lab-app は HMAC キーと JSON キー |
| 自己確認（objectstore の段階） | 6 件すべて期待どおり（書き込み用は原本を読めない・消せない、lab-app は原本に書けない・消せない、保持を外せない） |
| `./lab provider-requirements` | バケット名を埋めた IAM ポリシー 2 本、ライフサイクル 10 本、GCS のバインディングを出す |
| `test-smoke` | 75 件すべて OK |
| `test-audit` | 32 件中 31 件 OK（NG は Gmail 未サインインの「MCP の記録」。既知）。「原本は書き込み用・検索アプリ（lab-app）の資格情報では消せない」「管理者でも保持の回避を指定しなければ消せない」「閲覧の記録も消せない」はすべて OK |
| 片付け | managed の `./lab down` で全部消えた（サービスアカウント 2 つ、バケット、ロードバランサの部品、VM 4 台、ネットワーク）。API で確認: 残るのは既定のネットワークと削除済みのカスタムロール 3 つだけ。`.env` の鍵も消えた |

分かったこと: `render.vm_key_role` は役割の名前そのもの（`lab-app`）も受ける必要がある（`require_provided_env` が役割で回すため）。それ以外は机上どおり。

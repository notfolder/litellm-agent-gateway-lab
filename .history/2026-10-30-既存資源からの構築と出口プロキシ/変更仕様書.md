## 0. 背景と決定事項

### 0.1 背景

- `LAB_TARGET=aws-ec2` / `gcp-vm` は、構築ツールがクラウドの API で VPC・VM 3 台・バケット 6 つ・静的キーを作る前提だった（`.history/2026-10-30-VM環境の共通化とGCP追加/`）。
- 本番では、**S3 のバケット 1 つと VM 3 台が既に作られている状態**から構築する（ユーザー 2026-10-30）。ネットワーク・ファイアウォール・浮動 IP・VM の権限・静的キーも用意する側が持つ。
- 本番の VM は **Zscaler の中**にあり、外向きの通信は独自 CA で TLS を終端し直す中継を通る。検証環境でも同じ条件で構築できることを確かめる（ユーザー 2026-10-30、追加要件）。
- 本番の VM は arm とは限らない。自作イメージのビルドは **VM 上で行う**（本番も同じ。ユーザー 2026-10-30）。

### 0.2 決定事項（2026-10-30、ユーザーの回答）

| 項目 | 決定 |
|---|---|
| 既存の物の伝え方 | **`.env` に ID・名前を列挙する**（VM の ID 3 つ、バケット名、浮動 IP の ID、SSH の鍵と利用者名、静的キー）。タグやラベルを用意する側に求めない（1A） |
| バケット | **1 つ**。中をディレクトリ（`audit-raw/` など）で分け、保持は**オブジェクト単位**で付ける（原本 90 日、閲覧記録 400 日、他は無し）。バケット全体の既定の保持は使わない（2C、2 回目 1A） |
| 静的キー | **用意する側が役割ごとに発行し、`.env` で渡す**（3A）。クラスタの中の Pod（LiteLLM、整形、検索アプリ、Barman、registry）がオブジェクトストレージを S3 API で呼ぶために要る。VM の権限を全 Pod で共用すると役割分離が崩れ、GCP では HMAC キーがどうしても要る |
| 浮動 IP | **用意する側が浮動 IP と、VM に付け替えの権限を用意する**（4A）。今の keepalived 方式のまま |
| ネットワークの許可 | **ツールは触らない**（5A）。22、80/443、台の間の通信は用意する側が開ける。届かなければ案内して止まる |
| 障害試験の台の停止 | **操作者の資格情報で VM の停止・起動を行う**（6A。今のまま） |
| OS と CPU | **Ubuntu 24.04**。検証は arm で行い、CPU は VM から読んで自作イメージを同じアーキテクチャでビルドする（7A）。**ビルドは VM 上**（本番も同じ） |
| `./lab down` | **用意された物は残し、k3s をアンインストールし、保持の無いディレクトリを空にする**（8A）。**全削除の口も用意する**（`./lab down --all`。権限があれば VM・バケット・キーまで消す） |
| 表し方 | **同じ `LAB_TARGET` に `LAB_INFRA=managed` / `provided` の切り替えを足す**（9A） |
| Zscaler の方式 | **明示プロキシ**（環境変数で中継先を指定。2 回目 2B）。独自 CA を VM・k3s・Pod・操作者の Mac に配る |
| 操作者の Mac | **Mac も Zscaler の中にある想定で試す**（2 回目 3A）。`./lab` 自身の通信も中継を通す |
| 検証の形 | 検証環境では 4 台目の VM に中継（独自 CA で TLS を終端し直す）を置き、3 台の直接の外向き通信を塞いで `./lab up` と全試験を通す |

### 0.3 既存の仕様から変える方針

- **「作る」と「組み立てる」を分ける。** クラウドの資源を作る段階（provision）と、ある資源の上で k3s と Kubernetes の中を組み立てる段階（setup）を分け、setup は `.env` の ID だけを見る。`managed` は provision が `.env` を埋めてから setup を流し、`provided` は人が埋めた `.env` で setup だけを流す。1 つのコードで両方を試せる。
- **VM の初期化は SSH で流す。** ユーザーデータ（起動時）は使わない。既存の VM では起動時の仕掛けが使えないため。k3s の参加トークンと版は SSH で渡し、VM にバケットの読み取り権限を求めない。
- **バケットは 1 つ。** 論理名（`audit-raw` など）は 1 つのバケットのディレクトリになる。Mac の RustFS（4 バケット）と EKS 版は変えない。
- **クラウド固有層の関数の組**（変更設計書 2026-10-30 3.2 節）は、provision 用（作る・消す）と setup 用（読む・止める・起こす）に分かれる。

## 1. 対象範囲

| 対象 | 内容 |
|---|---|
| 構築ツール | `LAB_INFRA`、`.env` の既存資源の項目、provision と setup の分離、SSH での初期化、VM 上でのビルド、出口プロキシと CA の配布、`down --all` |
| クラウド固有層 | 1 バケットの作成（S3: Object Lock 有効・既定の保持なし、GCS: オブジェクト保持ロック有効）、ディレクトリ単位の権限、4 台目（中継）の作成、直接の外向き通信の遮断 |
| VM の中 | `vm/node-init.sh` を SSH 実行用に（トークンと版、CA、プロキシの環境変数、Docker の導入、起動時の外向き IP の復元） |

## 2. 要件

### 2.1 既存資源からの構築（`LAB_INFRA=provided`）

1. `.env` に次を書けば、`./lab up` が既存の VM 3 台とバケット 1 つの上に環境を組み立てる。
   - VM の識別子 3 つ（AWS はインスタンス ID、GCP は `<ゾーン>/<名前>`。順番が台の番号）
   - SSH の秘密鍵のパスと利用者名（`sudo` が使えること）
   - バケット名（1 つ）
   - 浮動 IP の識別子（AWS は割り当て ID、GCP はアドレスの名前）
   - 役割ごとの静的キー（litellm-writer、audit-compactor、audit-viewer、pg-backup、registry。GCP はさらに操作者）
   - 出口プロキシの URL と CA のファイル（Zscaler の中のとき）
2. ツールはネットワーク・ファイアウォール・浮動 IP・VM の権限・バケットの設定を**変更しない**。バケットの設定（Object Lock / オブジェクト保持ロックの有効、バージョニング）が合わなければ止まり、ライフサイクルの差は警告する。
3. 用意する側に渡す前提（VM の OS、開ける通信、バケットの設定、静的キーの権限）を設計書に 1 か所で書く。
4. `./lab down` は用意された物を残す。`./lab down --all` は `.env` の識別子の物をすべて消す（権限が無ければその旨を出して止まる）。
5. `managed` の振る舞いは今と同じ（`./lab up` で作って組み立て、`./lab down` で全部消す）。

### 2.2 1 バケットのディレクトリ構成とオブジェクト単位の保持

1. 論理名ごとのディレクトリ: `audit-raw/`、`audit-access/`、`audit-derived/`、`pg-backup/`、`images/`、`cluster/`。
2. 原本（`audit-raw/raw/`）は書き込み時に 90 日、閲覧記録（`audit-access/`）は 400 日の保持を付ける（日数は `.env` の既存の項目）。他のディレクトリは保持なし。保持の方式は S3 が Object Lock（GOVERNANCE / COMPLIANCE）、GCS がオブジェクト保持ロック（Unlocked / Locked）。
3. 役割ごとの権限は今の意味を保つ: 書き込み用は原本を読めず消せない、検索アプリは原本に書けない、どの利用者も原本と閲覧記録の版を消せず保持を回避できない。一覧（ListBucket）はバケット全体に許す。
4. Mac の RustFS は今の 4 バケットとバケット既定の保持のまま。

### 2.3 出口プロキシ（Zscaler 相当）の中での構築

1. `.env` に中継の URL と CA のファイルを書けば、VM・k3s（containerd を含む）・外へ出るすべての Pod・`./lab` 自身がその中継を通り、CA を信頼する。
2. 外へ出る Pod: LiteLLM、Gmail の MCP、cert-manager、Barman（PostgreSQL の sidecar）、registry、監査の整形・検索・試験の Job。
3. 検証環境（`managed`）では、`.env` の指定で 4 台目の VM に中継（mitmproxy、独自 CA）を置き、3 台の直接の外向き通信を遮断して、中継経由でしか外に出られない状態で全段階と全試験が通ることを確かめる。
4. 操作者の Mac も中継を通す（`./lab` の Python のクライアント、Helm）。SSH と kubectl（SSH の転送）は中継を通らない。

### 2.4 VM 上でのビルド

1. 自作イメージ 2 つ（LiteLLM、監査アプリ）は、k3s の台のどれか 1 台の Docker でビルドし、クラスタの中の置き場（registry）に push する。Mac の Docker は使わない。
2. アーキテクチャは VM のもの（arm64 でも amd64 でも同じ手順）。
3. ビルドの中の通信（ベースイメージの取得、pip）も中継を通り CA を信頼する。

## 4. リスク・注意事項

- **GCS のオブジェクト保持ロックは作成時に有効化**が要る（既存バケットは Console からのみ）。用意する側への前提に書く。
- **GCS は 1 バケットの「均一なバケットレベルのアクセス」を切る**（registry の S3 ドライバが ACL を付けるため。6 バケットのときは `images` だけだった）。権限は IAM で変わらない。
- **Object Lock を有効にしたバケットはバージョニングが外せない。** `down --all` では保持中の版が残る間は消せない（GOVERNANCE 相当なら操作者が回避して消せる）。
- **LiteLLM の外向き通信が中継を通るか**は配備で確かめる（httpx は環境変数を読む。aiohttp の経路は読まない可能性があるので、中継があるときは httpx に固定する）。
- **Mac の Go の道具（Helm）は `SSL_CERT_FILE` を読まない。** Helm には `--ca-file` を渡す。OCI のチャートで効くかは配備で確かめる。
- **中継を通す Mac の公開 IP の検出**は中継を通さずに行う（通すと中継の IP が返る）。

## 5. 用語

| 用語 | 意味 |
|---|---|
| provision | クラウドの資源（ネットワーク、VM、バケット、キー、浮動 IP、中継の VM）を作る段階。`managed` だけ |
| setup | `.env` の識別子の資源の上で、SSH で VM を初期化し、k3s と Kubernetes の中を組み立てる段階。両モード共通 |
| 出口プロキシ | 外向きの HTTP(S) を中継し、TLS を独自 CA で終端し直す装置。本番は Zscaler、検証は mitmproxy |
| オブジェクト単位の保持 | オブジェクトごとに「この日時まで消せない」を付ける仕組み。S3 の Object Lock の retention、GCS の Object Retention Lock |

# 変更設計書: 障害の試験の負荷を VPC の中（中継の VM）から送る

作成: 2026-11-05
状態: 実装済み・AWS で確認済み・docs/ に反映済み（2026-11-05）
この文書の役割: **どう作るか**。要件と決定は `変更仕様書.md`

## 1. 送り手（`tests/failover-load/remote_load.py`）

- 標準ライブラリだけで動く Python。中継の VM の `python3`（Ubuntu 24.04 に同梱）で動かす。
- 標準入力の 1 行目で設定（JSON: `url`、`key`、`rate`）を受け取る。マスターキーは引数にもファイルにも書かない（R3）。
- 1 秒に `rate` 件、要求ごとに別のスレッドで `POST <url>/v1/chat/completions`（`model: fake-tools`）を送り、結果を 1 件 1 行の JSON
  （`start`、`sent`、`elapsed`、`status`、`call_id`、`detail`）で標準出力に書く。要求ごとのスレッドなので、送り手が詰まって送る時刻が
  遅れることが無い（4.1 節の 4 の問題）。時間切れは 15 秒（Mac の送り手と同じ）。
- 中継の VM の環境変数のプロキシは使わない（`ProxyHandler({})`）。入口のホスト名は公開の DNS で内部 NLB の IP に引ける。
- 標準入力が閉じたら新しい要求をやめ、送り中の要求を待って終わる。

## 2. 受け手（`labtool/failover.py`）

- `RemoteLoad(Load)`: `run()` で送り手を中継の VM に置き（`vm.run_on`）、`vm.ssh_base(env, 中継の VM)` で `python3 -u` を起動して設定を
  標準入力に書き、標準出力の行を `Sample` にして `samples` に足す。止めるときは標準入力を閉じ、終わるのを待つ（30 秒で打ち切り）。
- `make_load(env)`: VM の環境で managed、かつ中継の VM（`LAB_VM_PROXY_NODE`）があれば `RemoteLoad`、それ以外は `Load`（R4）。
- `run_scenario` と `ops.upgrade_k8s(--measure)` は `make_load` を使う。判定の数え方は変えない（R2）。
- `wait_redis_clean`（回復の後の Redis の確かめ）は少量の要求なので、今までどおり Mac から送る。

## 3. 試験

- 単体テスト: 送り手の 1 行を `Sample` に戻す関数（`failover._sample_from_line`）と、`make_load` の選び方。
- 配備: AWS（`aws-ec2`、managed）で全場面。結果は 4 章。

## 4. 配備と試験の結果

2026-11-05 15:55〜16:56、AWS（`aws-ec2`、managed）。構築から片付けまでを 1 本の台本で流した（16:56 に有料の資源 0 件）。

1. 中継の VM から送っても、LiteLLM が ready に戻った後の失敗（TLS の握手の時間切れ、接続の拒否、証明書の検証の失敗）は続いた。
   `.history/2026-11-05-1台だけの部品の冗長化/変更設計書.md` 4.1 節の「Mac の転送の側の失敗」という推定は誤り。
2. **原因: 止めていない台の Traefik が生存確認（`/ping`、時間切れ 2 秒、3 回）に応答できず、Kubernetes に再起動させられた**。
   pg-node で 2 台（16:28:21 と 16:28:59。片方を 16:29:22 に再起動）、valkey-node と entry-node でも 1 台ずつ再起動した。
   止まっている間は接続の拒否と握手の時間切れ、起動の直後は証明書を読み込む前の既定の証明書で応答して検証に失敗する。
3. 推定の理由: k3s の Traefik（DaemonSet）は CPU とメモリの要求（`requests`）を持たない（BestEffort）。台の CPU の要求の合計は
   node1 で 97%、node2 で 74%（16:34 の時点）。台が 1 台止まると、LiteLLM などが残りの台に移って一斉に起動し、CPU が混む。
   BestEffort の Traefik は CPU の取り分が最も少なく、生存確認に応答できなかったと見る（台ごとの CPU の時系列は取っていない）。
4. 段階 1（入口と止めた台の Pod が外れるまで）と段階 2（PostgreSQL の切り替えの間の 503）は、11/5 15 時の調査と同じ形で出た。

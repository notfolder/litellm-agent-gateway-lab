## 2. RustFS

### 2.1 構成

| 項目 | 内容 |
|---|---|
| イメージ | `rustfs/rustfs:1.0.1`（2026-10-03 の最新の安定版） |
| 起動の設定 | `RUSTFS_VOLUMES=/data`、`RUSTFS_ADDRESS=0.0.0.0:9000`、`RUSTFS_CONSOLE_ENABLE=false`。1 台 1 ディスク（Object Lock は 1 台 1 ディスクでも動くことを、RustFS の公式の結合試験で確認） |
| 置くノード | server ノード（`k3d-litellm-server-0`）に固定する（`nodeSelector`）。障害の試験で止めるのは agent ノードだけなので、試験で RustFS が止まらない（10 章） |
| ディスク | local-path、10Gi |
| Service | `rustfs`（9000: S3 API）。クラスタの外には出さない |
| 資源 | requests 128Mi / limits 256Mi |
| 管理者 | 環境変数 `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY`。値は `.env` の `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` に生成する（旧名の `RUSTFS_ROOT_USER` / `RUSTFS_ROOT_PASSWORD` は使わない） |

### 2.2 構築ツールからのつなぎ方

`./lab` は Mac の上で動くので、クラスタの中の名前（`rustfs:9000`）には届かない。

- 構築ツールが S3 や RustFS の管理 API を使うとき（`objectstore` の段階、`test-audit`、`audit-synth`、`audit-compact`、`test-failover` の欠けの照合）は、その間だけ `kubectl port-forward svc/rustfs <空いているポート>:9000` を張り、`http://127.0.0.1:<ポート>` に接続する。終わったら閉じる（`with` で包む）。
- Pod の中からは `.env` の `LAB_S3_ENDPOINT`（既定 `http://rustfs:9000`）を使う。

### 2.3 バケットの設定

| バケット | バージョニング | Object Lock の既定の保持 | ライフサイクル |
|---|---|---|---|
| `audit-raw` | 有効 | `LAB_AUDIT_LOCK_MODE`（検証 `GOVERNANCE`、本番 `COMPLIANCE`）、`LAB_AUDIT_RETENTION_DAYS` 日（90） | 現行版・旧版とも 保持日数 + 1 日で期限切れ |
| `audit-access` | 有効 | `audit-raw` と同じ方式、`LAB_AUDIT_ACCESS_RETENTION_DAYS` 日（400） | 現行版・旧版とも 保持日数 + 1 日で期限切れ |
| `audit-derived` | 有効 | なし | 接頭辞ごと（下の表） |
| `pg-backup` | 無効 | なし | なし（Barman の保持設定で消す） |

`audit-derived` の接頭辞ごとのライフサイクル:

| 接頭辞 | 現行版 | 旧版 |
|---|---|---|
| `meta/` | 91 日 | 1 日（作り直しの前の版は要らない） |
| `usage_daily/` | 400 日 | 1 日 |
| `billing/settlement/` | 400 日 | 400 日（計算し直しの履歴。仕様 6.7） |
| `billing/contracts/`、`billing/fx_rates/` | 消さない。編集のたびに新しいファイルを足すので「最新の 1 件だけ残す」は期限切れの規則では表せず、小さく編集も稀なので、すべて残す（7.3 節） | — |
| `synth/` | 7 日 | 1 日 |

- 書き込みはどれも、バケットの既定の保持で自動的にロックがかかる（書く側はロックの指定をしない）。保持の期間が違うものはバケットを分ける。
- 検証環境では RustFS のディスクがクラスタの中にあるので、`./lab down` と `./lab rebuild` で中身も消える。
- Object Lock のバケットへの PUT には `Content-MD5` などの検査値が要る。boto3 は自動で付ける。
- RustFS では、Object Lock を有効にしたバケットに、0 日の期限切れと MinIO 拡張の削除マーカーの期限切れ（`DelMarkerExpiration`）は設定できない。どちらも使わない。旧版の期限切れ（`NoncurrentVersionExpiration`）は使える。

### 2.4 利用者と権限

| 利用者 | 許可する操作 |
|---|---|
| `litellm-writer` | `s3:PutObject` on `audit-raw/raw/*` |
| `audit-compactor` | `s3:GetObject`、`s3:ListBucket` on `audit-raw`。`s3:GetObject`、`s3:PutObject`、`s3:ListBucket` on `audit-derived` |
| `audit-viewer` | `s3:GetObject`、`s3:ListBucket` on `audit-raw`、`audit-access`、`audit-derived`。`s3:PutObject` on `audit-access/*`、`audit-derived/billing/contracts/*`、`audit-derived/billing/fx_rates/*` |
| `pg-backup` | `s3:*` on `pg-backup` |

どの利用者にも、`audit-raw` と `audit-access` の削除と、保持の回避（`s3:BypassGovernanceRetention`）は許さない。

### 2.5 冪等性

`./lab objectstore` は、2.2 節のつなぎ方で、S3 の API（boto3。構築ツールの依存に足す）で次を行う。

1. バケットが無ければ作る（`audit-raw` と `audit-access` は Object Lock を有効にして作る）。
2. バケットの設定（バージョニング、既定の保持、ライフサイクル）を読み、違えば書く。`audit-raw` か `audit-access` の Object Lock が無効のまま存在する場合はエラーで止める（後から有効にできないため）。
3. 利用者と権限は、RustFS の管理 API（`/rustfs/admin/v3`。JSON を SigV4〔サービス名 `s3`、リージョン `us-east-1`〕で署名して送る）で、無ければ作り、違えば直す。Python から botocore の署名と HTTP で呼ぶ。
   - 利用者の追加: `PUT /rustfs/admin/v3/add-user?accessKey=<名前>`（本文に `secretKey` と `status`）
   - 権限の定義: `PUT /rustfs/admin/v3/add-canned-policy?name=<名前>`（本文に S3 の権限の JSON。接頭辞ごとの指定が使える）
   - 割り当て: `PUT /rustfs/admin/v3/set-user-or-group-policy?policyName=<名前>&userOrGroup=<利用者>&isGroup=false`
4. 最後に自己確認をする: 各利用者で、許した操作ができ、許していない操作（原本の削除、保持の回避なしの削除）が拒否されることを確かめる（実装の段 1 の終わりの条件。仕様 10 章）。

### 3.3 `Pooler` `litellm-pg-pooler-rw`

| 項目 | 値 |
|---|---|
| `type` | `rw` |
| `instances` | 2（Pod の anti-affinity は preferred） |
| `pgbouncer.poolMode` | `transaction` |
| `pgbouncer.parameters` | `max_client_conn: "1000"`、`default_pool_size: "40"`、`max_prepared_statements: "0"` |

`max_prepared_statements` を 0 にする理由:

- LiteLLM が使う Prisma は 5.4.2（prisma-client-py 0.11.0）。URL に `pgbouncer=true` を付けると、問い合わせの使い回しの保存は止まるが、問い合わせごとの準備（prepare）は続け、トランザクションの初めに `DEALLOCATE ALL` を送る。
- この形と、PgBouncer の準備済みの問い合わせの機能（`max_prepared_statements` が 0 より大きい）を組み合わせると、`prepared statement "PGBOUNCER_x" does not exist` で失敗する既知の問題がある（prisma#21799。直されないまま閉じられた）。
- 0 にすると PgBouncer はこの機能を使わず、Prisma が `pgbouncer=true` で想定している従来の動き方になる。
- PgBouncer は 1.24 から既定が 200 になったので、明示して 0 にする。

### 3.4 LiteLLM の接続設定

Helm チャートの DB の設定（`litellm/values.yaml` の `db`）を次のように変える。チャートは `db.useExisting: true` のとき、`DATABASE_URL` を `postgresql://$(DATABASE_USERNAME):$(DATABASE_PASSWORD)@$(DATABASE_HOST)/$(DATABASE_NAME)` の形で Pod の `env` に直接書く。`env` に直接書いた値は Secret（`envFrom`）より優先されるので、Secret で `DATABASE_URL` を渡す形にはしない。

| 値 | 今 | 変更後 |
|---|---|---|
| `db.useExisting` | `true` | `true`（変えない） |
| `db.endpoint` | `postgres` | `LAB_DB_POOLER` が `pooler` なら `litellm-pg-pooler-rw`、`direct` なら `litellm-pg-rw`（構築ツールが上書き用の値に入れる） |
| `db.secret.name` | `postgres` | `litellm-pg-app`（キー `username` / `password` はそのまま） |
| `migrationJob.enabled` | `true` | `false`（3.5 節の自前の Job にする） |
| `envVars.DISABLE_SCHEMA_UPDATE` | （チャートが入れていた） | `"true"`。チャートは `migrationJob.enabled: true` のときだけこれを自動で入れるので、自分で入れる。チャートは同じ名前を重ねて書かない（重複でインストールが失敗した過去の事例とはぶつからない） |

| `LAB_DB_POOLER` | `database_connection_pool_limit` | 追加の設定 |
|---|---|---|
| `pooler` | 10 | `envVars.DATABASE_DISABLE_PREPARED_STATEMENTS: "true"`（LiteLLM が URL に `pgbouncer=true` を足す。値は `true` と書く。決まった値以外は起動に失敗する） |
| `direct` | 5（最大 4 Pod で 20 本、`max_connections` 200 に収まる） | なし |

- サービング用の Pod には `DIRECT_URL` を置かない（移行を止めているので使われない）。
- 移行を止めていても、起動のたびにスキーマの差分の確認（`prisma migrate diff`）が `DATABASE_URL`（Pooler）経由で走る。失敗しても例外を出さない作りなので、起動は止まらない。
- `values.yaml` の `migrationJob` と `DISABLE_SCHEMA_UPDATE` についてのコメント（24 行目）も直す。

### 3.5 DB 移行の Job

- `./lab litellm` の中で、helm の更新の前に流す。
- 名前は `litellm-migrate-<ハッシュ>`。ハッシュは、LiteLLM のイメージのタグと、`Cluster` `litellm-pg` の `metadata.uid` から作る（DB を作り直すと uid が変わるので、移行が流れ直る）。
- 同じ名前の Job が成功済みなら流さない。そのため **`ttlSecondsAfterFinished` は付けない**（付けると Job が消え、成功済みの判定ができない）。古いハッシュの Job は、新しい Job が成功したら消す。
- 直結の接続先は Secret `litellm-migrate-db` の `DATABASE_URL` に置く（構築ツールが `litellm-pg-app` の値から `postgresql://litellm:<pw>@litellm-pg-rw:5432/litellm` を組み立てて作る）。
- 中身は、公式の Helm チャートの移行の Job と同じ:

```yaml
image: <LiteLLM と同じイメージ>
workingDir: /app
command: ["python", "litellm/proxy/prisma_migration.py"]
env:
  - name: DATABASE_URL          # Secret litellm-migrate-db から。直結（litellm-pg-rw）。Pooler は通さない
  - name: DISABLE_SCHEMA_UPDATE
    value: "false"
  # DATABASE_DISABLE_PREPARED_STATEMENTS は付けない（付けると直結の URL にも pgbouncer=true が付く）
  # --config は渡さない（この入口は設定を読まない）
restartPolicy: OnFailure
backoffLimit: 4
activeDeadlineSeconds: 1800
```

- この入口は `prisma migrate deploy` を流して終わる。失敗すると 0 以外で終わる。
- 構築ツールは完了まで待ち（最大 5 分）、失敗したらログを表示してエラーで止める。

### 3.6 今の PostgreSQL から消すもの

`./lab datastores` の中で、無ければ何もしない（`--ignore-not-found`）形で消す。2 回目以降に流しても失敗しない。

- StatefulSet と Service の `postgres`、PVC `data-postgres-0`
- Secret `postgres`
- `values.yaml` の `db.secret.name: postgres`、`db.endpoint: postgres`（3.4 節で置き換える）

## 4. Valkey と Sentinel

### 4.1 構成

| 項目 | データの Pod（`valkey`） | 監視の Pod（`valkey-sentinel`） |
|---|---|---|
| イメージ | `valkey/valkey:9.0.6` | 同じ（Sentinel は `valkey-sentinel` か `valkey-server <設定> --sentinel` で起動する。どちらもイメージに入っている） |
| 台数 | 3 | 3 |
| Service | headless `valkey-headless`（6379） | headless `valkey-sentinel-headless`（26379）と通常の `valkey-sentinel`（26379） |
| ディスク | local-path 1Gi（`/data`） | local-path 64Mi（`/conf`。Sentinel が設定を書き換えるため） |
| 資源 | requests 128Mi / limits 256Mi | requests 32Mi / limits 64Mi |
| anti-affinity | required（ホスト名） | required（ホスト名） |
| PDB | `maxUnavailable: 1` | `maxUnavailable: 1` |

### 4.2 データの Pod の設定（`valkey.conf`）

```
appendonly yes
appendfsync everysec
save 900 1
maxmemory 128mb
maxmemory-policy noeviction
min-replicas-to-write 1
min-replicas-max-lag 10
requirepass <REDIS_PASSWORD>
masterauth <REDIS_PASSWORD>
replica-announce-ip <自分の DNS 名: valkey-N.valkey-headless.litellm-lab.svc.cluster.local>
```

パスワードは、今の `.env` の `REDIS_PASSWORD` を使い回す（LiteLLM も同じ名前の環境変数で読むので、名前を変えない）。

### 4.3 Sentinel の設定（`sentinel.conf` のひな形）

```
port 26379
sentinel resolve-hostnames yes
sentinel announce-hostnames yes
sentinel announce-ip <自分の DNS 名>
requirepass <SENTINEL_PASSWORD>
sentinel sentinel-pass <SENTINEL_PASSWORD>   # Sentinel 同士の認証（requirepass を付けると要る）
sentinel monitor mymaster <起動時に決めた primary の DNS 名> 6379 2
sentinel auth-pass mymaster <REDIS_PASSWORD>
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 60000
sentinel parallel-syncs mymaster 1
```

### 4.4 起動スクリプト（ConfigMap `valkey-scripts`）

データの Pod（`start-valkey.sh`）:

1. Sentinel（`valkey-sentinel` の Service）に `SENTINEL get-master-addr-by-name mymaster` を聞く（3 回まで、1 秒間隔）。
2. 答えがあり、それが自分でなければ `replicaof <その DNS 名> 6379` を設定に足して起動する。自分なら primary として起動する。
3. 答えが無ければ、自分が `valkey-0` なら primary、そうでなければ `valkey-0` の replica として起動する。

Sentinel（`start-sentinel.sh`）:

1. `/conf/sentinel.conf` があれば、それを使って起動する（Sentinel が持っている最新の状態を優先する）。
2. 無ければ、ほかの Sentinel に primary を聞き、答えが無ければ `valkey-0` を primary としてひな形から作る。

### 4.5 LiteLLM の設定

| 設定 | 値 |
|---|---|
| `REDIS_SENTINEL_NODES` | `[["valkey-sentinel-0.valkey-sentinel-headless",26379],["valkey-sentinel-1.…",26379],["valkey-sentinel-2.…",26379]]` |

## 5. 監査ログ

### 5.1 書き込みの方式（決定の根拠）

LiteLLM に元からある S3 への出力（`s3_v2`）を、使っている版（v1.104.2）のソースで確かめた結果（`litellm/integrations/s3_v2.py`、`litellm/integrations/s3.py`、`litellm/constants.py`）:

| 項目 | 元からある出力の振る舞い |
|---|---|
| 置き方（既定） | 1 件 1 ファイル。`<s3_path>/[チームの別名/][キーの別名/]YYYY-MM-DD/time-HH-MM-SS-ffffff_<id>.json` |
| まとめて書く設定（`s3_batch_file_upload: true`） | 書き出しのたびに、日付のフォルダごとに 1 ファイル。`<s3_path>/YYYY-MM-DD/batch_HH-MM-SS_<uuid>.jsonl`。cold storage として使うときは無効になる |
| 書き出しの間隔 | 10 秒か 512 件（`DEFAULT_S3_FLUSH_INTERVAL_SECONDS`、`DEFAULT_S3_BATCH_SIZE`。環境変数で変えられる） |
| 中身 | `StandardLoggingPayload` をそのまま JSON にしたもの（入力のメッセージ、応答、トークン数、費用、キーの持ち主、ガードレールの情報を含む）。**圧縮しない** |
| Object Lock | PUT に `Content-MD5` を付けるので、既定の保持があるバケットに書ける |
| 書けないとき | 3 回まで再送（1 秒、2 秒）。だめなら次の書き出しに回し、`s3_max_retry_age_seconds` を超えたら捨てて警告のログを出す。**ディスクへの退避は無い**（メモリの中だけ） |

自作のコールバックにする理由:

| 理由 | 中身 |
|---|---|
| 保存量が約 5 分の 1 になる | 元からある出力は圧縮しない。本文を 90 日残す決定（仕様 0.2）のもとでは、本番の規模で 90 日 約 90 TB と約 18 TB の差になる（仮定の値。実測で直す）。AWS S3 はストレージ側で圧縮しないので、置き換え先を選ばずに効く方法は書く側での圧縮しかない |
| 書けないときの振る舞いが決定と合う | 決定（仕様 0.2）は「退避してから、上限を超えたら捨てて数える」。元からある出力は退避せず、メモリの中で待ってから捨てる |
| 記録と本文を分けて書ける | 小さな記録の流れを別に書くので、整形の処理が本文（1 日 200 GB 規模）を読まずに済む |
| 審査の判定を同じ流れに書ける | 判定を、要求と同じ ID で同じ置き場に書ける |

元からある出力から引き継ぐもの: 中身は `StandardLoggingPayload` をそのまま使う（LiteLLM が文書で定めている形で、版が上がっても追いやすい）。

### 5.2 経路ごとの記録の届き方（今の構成）

| 経路 | `call_type` | 記録の届き方（v1.104.2 のソースで確認） |
|---|---|---|
| Codex など（`/v1/responses`、`/v1/chat/completions`） | `aresponses` / `acompletion` | 成功時・失敗時のフックに届く。ストリーミングも、組み立て後の応答とトークン数・利用料が入る |
| Claude Code（`/v1/messages`） | `anthropic_messages` | 同上。`messages` は Anthropic の形の要求のメッセージ（system を足したもの）、`response` は LiteLLM が OpenAI の形に変換したもの。審査のガードレールは User-Agent を見て審査を省くが、記録はほかの要求と同じく残る |
| MCP（`/<サーバー名>/mcp` の `tools/call`） | `call_mcp_tool` | 成功時・失敗時とも届く。`model` は `MCP: <ツール名>`。引数は `metadata.mcp_tool_call_metadata.arguments`、`response` はツールの結果 |
| 素通しの中継（`/anthropic/...` など） | — | 今の入口で 403 にしている（`k8s/ingress.yaml` の deny-all）。記録の対象外 |
| 審査官の呼び出し（ガードレールの中の `llm_router.acompletion`） | `acompletion` | 何もしなければ、利用者の無い要求として届く。5.3 節の指定で届かないようにする |
| Jev の一次判定（ガードレールの中の `litellm.adecisions`） | — | 同上（`@client` が付いているのでフックに届く）。5.3 節の指定で届かないようにする |

### 5.3 コールバック（`litellm/guardrails/audit_log.py`）

| 項目 | 内容 |
|---|---|
| 形 | `CustomLogger` を継承した `AuditLogger`。設定の `litellm_settings.callbacks` に `audit_log.audit_logger_instance` を足す |
| フック | `async_log_success_event`、`async_log_failure_event`。`kwargs["standard_logging_object"]` と `kwargs["litellm_call_id"]` を受け取る |
| 結び付けの ID | `litellm_call_id`（LiteLLM が要求ごとに付ける ID。応答の見出し `x-litellm-call-id` にも出る）。`StandardLoggingPayload.id` は上流の応答の ID（`chatcmpl-…`、`resp_…`、`msg_…`）なので、結び付けには使わない |
| 審査の受け口 | `audit_log.record_review(entry: dict)`。審査のガードレールが判定のたびに呼ぶ（同じプロセスの中）。`entry` に `request_call_id`（ガードレールの `data["litellm_call_id"]`）を入れる。今の判定ログの `event: review` のものだけを渡し、`event: pass_through`（審査を省いた印）は渡さない |
| ガードレールの中の呼び出しを記録しない | 審査官（`llm_router.acompletion`）と Jev（`litellm.adecisions`）の呼び出しに、`**{"no-log": True}` と `metadata={"tool_call_review_internal": True}` を付ける。`no-log` で自作のコールバックは呼ばれない。念のため、`metadata` にこの印がある記録はコールバックの側でも捨てる |
| 審査の利用量 | 審査官の戻り値の `usage` と `_hidden_params["response_cost"]` を、審査の結果（`Verdict`）に持たせて審査の記録に書く。やり直し（最大 3 回）をしたときは、応答が返った回の分をすべて足す。ガードレールの費用（`guardrail_cost`）は使わない（使うと元の要求の利用料に足され、二重になる） |
| バッファ | 記録用（NDJSON の行）と本文用（gzip の部品）を Pod の中に溜める |
| 書き出しの条件 | `LAB_AUDIT_FLUSH_SECONDS`（検証 10 秒、本番 60 秒）たった、本文が 64 MB に達した、プロセスが止まる |
| 止まるときの書き出し | Pod の止まり方は、preStop の `sleep 10` → SIGTERM → LiteLLM が処理中の要求を待つ → プロセスの終了、の順。処理中の要求の記録はこの途中で届くので、最後の書き出しは、処理中の要求を待ち終えた後（`atexit` で登録した関数）で行う。自分で SIGTERM の受け口は入れない（LiteLLM の受け口を上書きしてしまう）。preStop 10 秒と待ちと書き出しを、`terminationGracePeriodSeconds`（既定 90 秒）の中に収める |
| 書き出しの処理 | 専用のスレッドで boto3 の `put_object`。要求の処理（イベントループ）を待たせない |
| 退避 | 書けなければ `/var/lib/audit-spool`（emptyDir、`sizeLimit: 1Gi`）にファイルとして置き、30 秒ごとに再送する |
| 捨てる | 退避が 900 MiB を超えたら新しい記録を捨てる（上限ちょうどまで溜めると、kubelet が Pod を追い出すため）。件数を `audit_log_dropped_total` に足し、警告のログを 1 分に 1 回出す |
| 止まるときに残った退避 | S3 に書けないまま止まると、退避した記録は Pod と一緒に消える（仕様の決定どおり受け入れる）。止まる直前に、残っていた件数を `audit_log_lost_on_shutdown` として警告のログに出す |
| 数える | `audit_log_written_total`、`audit_log_spooled_bytes`、`audit_log_dropped_total` を、標準出力の JSON（1 分に 1 回）で出す。監視の仕組みへのつなぎ込みは 1 版目の範囲外 |
| S3 の資格情報 | Secret `litellm-secrets` に `AUDIT_S3_ACCESS_KEY`、`AUDIT_S3_SECRET_KEY` を足す。接続先などは `values.yaml` の `envVars`（`AUDIT_S3_ENDPOINT`、`AUDIT_S3_REGION`、`AUDIT_S3_BUCKET`、`AUDIT_FLUSH_SECONDS`） |
| `values.yaml` に足すもの | 退避用の `volumes`（emptyDir、`sizeLimit: 1Gi`）と `volumeMounts`（`/var/lib/audit-spool`） |
| 今の判定ログ | 審査のガードレールの標準出力への判定ログと `./lab review-log` は、そのまま残す（`review-log` は `tool_call_review ` で始まる行だけを読むので、影響しない） |

### 5.4 置き場所

```
audit-raw/
  raw/meta/dt=YYYY-MM-DD/hour=HH/<pod>-<書き出しの開始時刻>-<連番>.ndjson.gz
  raw/body/dt=YYYY-MM-DD/hour=HH/<pod>-<書き出しの開始時刻>-<連番>.gz
audit-access/
  view/dt=YYYY-MM-DD/hour=HH/<pod>-<時刻>-<連番>.ndjson.gz
  admin/dt=YYYY-MM-DD/<pod>-<時刻>-<連番>.ndjson.gz
audit-derived/
  meta/dt=YYYY-MM-DD/hour=HH/part-0.parquet
  usage_daily/dt=YYYY-MM-DD/part-0.parquet
  billing/contracts/<時刻>-<pod>.json
  billing/fx_rates/<時刻>-<pod>.json
  billing/settlement/month=YYYY-MM/part-0.parquet
  synth/...                                  # 合成データ（試験用）
  _state/compactor.json
```

- **`dt` と `hour` は日本時間（JST）で区切る。** 記録の `ts_start`（UTC で書く）を日本時間に直して決める。審査の記録は、ガードレールが判定した時刻で区切る（要求とは別の時間に入ることがある。整形の処理で吸収する。5.8 節）。1 回の書き出しに複数の時間が混ざるときは、時間ごとに別のファイルにする。
- ファイル名の時刻も日本時間で書く（`20261011T0905JST` の形）。
- 名前は Pod 名、時刻、連番で一意にし、同じ名前に二度書かない。

### 5.5 記録の形（`raw/meta` の 1 行）

共通の項目:

| 項目 | 型 | 内容 |
|---|---|---|
| `schema` | int | 形の版。今は `1` |
| `type` | str | `request` / `mcp` / `review` |
| `call_id` | str | `litellm_call_id`。要求と審査を結び付ける |
| `ts_start` / `ts_end` | str | ISO 8601、UTC（`Z` 付き）、ミリ秒。区切りと表示は日本時間に直して使う |
| `pod` | str | 書いた Pod |

`request` と `mcp` の項目（出どころは `StandardLoggingPayload`。カッコ内）:

| 項目 | 出どころ |
|---|---|
| `response_id` | `id`（上流の応答の ID） |
| `user_id` | `metadata.user_api_key_user_id`。無ければ空（マスターキーでの試験など。精算では「利用者なし」） |
| `user_email` | `metadata.user_api_key_user_email`（キーに利用者が結び付いているときに入る。チームのキーなどでは空） |
| `team_id` / `team_alias` / `key_alias` / `key_hash` | `metadata.user_api_key_team_id` / `…_team_alias` / `…_alias` / `…_hash` |
| `end_user` | `end_user` |
| `client` | User-Agent から `codex` / `claude-code` / `unknown`（User-Agent が空）/ `other`。審査のガードレールの判定の関数（`tool_call_review.py` の `_client_kind`）を共通の部品に移して使う |
| `session_id` / `trace_id` | `session_id` / `trace_id` |
| `call_type` | `call_type`。`type` はここから決める（`call_mcp_tool` なら `mcp`、それ以外は `request`） |
| `model_group` / `model` / `model_id` / `api_base` | 同名 |
| `status` / `error_class` | `status` / `error_information.error_class` |
| `tokens_in` / `tokens_out` | `prompt_tokens` / `completion_tokens` |
| `tokens_cache_read` / `tokens_cache_write` | `metadata.usage_object.prompt_tokens_details.cached_tokens` / `…cache_write_tokens`（Anthropic の `cache_read_input_tokens` / `cache_creation_input_tokens` も LiteLLM がここに変換して入れる） |

### 5.6 本文の形（`raw/body`）

- ファイルは、1 件ごとに独立した gzip の部品を順につないだもの。ファイル全体も通常の gzip として展開できる。
- 1 件の中身（展開後）: `{"schema": 1, "call_id": <litellm_call_id>, "payload": <StandardLoggingPayload をそのまま>}`。
- 本文が消されないよう、LiteLLM の `turn_off_message_logging` は有効にしない。

### 5.8 整形の定期処理（audit-compactor）

| 項目 | 内容 |
|---|---|
| 起動 | CronJob、毎時 10 分（日本時間）。`concurrencyPolicy: Forbid`。資格情報は Secret `audit-compactor-s3` |
| 対象の見つけ方 | `_state/compactor.json` に、時間ごとの「原本のファイルの数と、最も新しい更新時刻」と、`billing/contracts/` と `billing/fx_rates/` の最新の版の名前を持つ。今の状態と違うものを、古い順に処理する（遅れて届いた記録も拾える） |
| 時間ごとの処理 | 時間 H は、H と H+1 の両方が締まってから処理する（審査の記録は、要求より後の時間に入ることがあるため）。H の `request` / `mcp` を読み、H と H+1 の `review` を `request_call_id` = `call_id` で結び付け（審査の結果、理由、Jev の確率、審査の A の額）、`user_id`, `ts_start` の順に並べて `meta/.../part-0.parquet` に書く。行グループ 10 万行、zstd |
| 日ごとの処理 | 日本時間の日の全時間を処理したら、`usage_daily` を作る（遅れて届いた記録でその日の時間を処理し直したら、`usage_daily` も作り直す）。キーは `user_id`（空は「利用者なし」）、`user_email`、`team_id`、`model_group`、`model`、`client`、`category`（`request` / `review`）。値は件数、トークン数、`cost_usd` の合計。`category: review` の行は、`model_group` と `model` を審査官のもの（`judge_model_group`）にし、利用者・チーム・クライアントは結び付けた要求のものにする |
| 精算 | 毎回、当月の精算を作り直す。前月までの精算は、その月の `usage_daily`、請求の単位の定義、換算のレートのどれかが変わったときに作り直す（7.2 節）。作り直した前の版は、`audit-derived` のバージョニングで 400 日残る（計算し直しの履歴） |
| 冪等性 | 同じ時間を処理し直すと、同じ名前に同じ内容を書く |
| 資源 | requests 256Mi / limits 1Gi。DuckDB の `memory_limit` を 768MB にする |

| DuckDB | 1.5 系（2026-09-28 時点の最新は 1.5.6）。要求ごとに接続を作る。S3 の接続は `CREATE SECRET (TYPE s3, KEY_ID …, SECRET …, ENDPOINT …, URL_STYLE 'path', USE_SSL …, REGION …)` で与える。`ENDPOINT`、`USE_SSL`、`REGION` は `LAB_S3_ENDPOINT`（スキームを外して `ENDPOINT` に、`https` なら `USE_SSL true`）と `LAB_S3_REGION` から組み立てる（古い `SET s3_endpoint` の方式は使わない） |
| 資格情報 | Secret `audit-viewer-s3`、`audit-viewer-oidc`、`audit-viewer-session` |
| CSRF | 書き込みを伴う API（`POST`、`PUT`）は、セッションに結び付けた確認用の値（ヘッダー `X-CSRF-Token`）を必須にする。htmx の要求に自動で付ける |
| 時刻 | 画面の表示と期間の指定は日本時間。API の `from` / `to` は日本時間の日付か、時差付きの ISO 8601 |

### 6.2 サインインと役割

- OpenID Connect。設定は `.env` の `LAB_AUDIT_OIDC_ISSUER`（既定 `https://accounts.google.com`）、`LAB_AUDIT_OIDC_CLIENT_ID` / `LAB_AUDIT_OIDC_CLIENT_SECRET`（既定は Google の OAuth クライアントと同じ値）。本番の Entra ID は、この 3 つを Entra ID の値にするだけで切り替わる。
- 戻り先の URL は `<base_url>/lab-audit/auth/callback`（`base_url` は構築ツールの `Env.base_url`。`LAB_HTTP_PORT` を変えると変わる）。検証環境では Google の OAuth クライアントにこの URL を足す（1 つのクライアントに複数の戻り先を登録でき、`http://localhost` は HTTPS の例外として認められている）。`docs/setup-google.md` と `README.md` の戻り先の一覧に足す。
- OIDC の設定が無いとき（Google の手作業の準備をしていないとき）は、`./lab audit` の段階で検索アプリを入れず、そのことを表示する（今の構築ツールの「手作業の準備が無い部品は無効にする」方針と同じ）。整形の定期処理は入れる。
- 役割: `LAB_AUDITORS` に含まれれば監査担当、`LAB_AUDIT_ADMINS`（既定は `LAB_USER1_EMAIL`）に含まれれば管理者、それ以外は一般の利用者。本番では `LAB_AUDIT_ROLE_CLAIM`（例 `groups`）で、ID トークンのグループから役割を決められるようにする。
- 一般の利用者の絞り込みは、サインインしたメールアドレスと、記録・日次の集計・精算の `user_email` の一致で行う（検証環境のキーはすべて利用者に結び付いているので `user_email` が入る）。
- セッション: 署名付きの Cookie（`AUDIT_SESSION_SECRET`）、8 時間で切れる。

### 6.4 検索の処理

| 対象 | 読むもの |
|---|---|
| 利用量 | `usage_daily` がある日はそれを読む。無い日（今日、まだ締まっていない前日など）は、その日の時間ごとの Parquet と、まだ整形していない時間の `raw/meta` から集計して足す |
| 履歴 | 期間の時間ごとの Parquet を読み、`user_id` で絞る（並び順のおかげで、関係のない行グループは読まない）。まだ整形していない時間は `raw/meta` を読む |

速さの目標（仕様 7.4）に届かないときの手立て: 整形の処理で、利用者ごとの索引（`user_id` × 日 → 記録のある時間の一覧）を作る。それでも足りなければ、`user_id` のハッシュで Parquet を分ける。

## 7. 利用料の計算

### 7.1 A（概算）

- LiteLLM が出す `response_cost` をそのまま使う。
- Claude のモデル（今の設定の `anthropic/*`）は LiteLLM の単価表に載っているので、設定しなくても A が出る（Claude Max の定額でも、単価表の値で概算する）。
- 単価を設定するのは `chatgpt/` のモデルだけ。`model_info` に `input_cost_per_token`、`output_cost_per_token`、`cache_read_input_token_cost` を設定する。
- `.env` の名前: `LAB_PRICE_<名前>_IN` / `_OUT` / `_CACHE_READ`（1 百万トークンあたりの USD）。`<名前>` は LiteLLM の設定の `model_name`（例 `review-judge`、Codex 用のモデル名）を大文字にし、英数字以外を `_` にしたもの（例 `review-judge` → `LAB_PRICE_REVIEW_JUDGE_IN`）。今の `.env` の読み込み（キーは英数字と `_` だけ）で読める。
- 単価の既定値: その `model_name` が指す ChatGPT のモデルと同じ名前の、OpenAI の API の公開価格。同じ名前が無ければ、同じ格（大・中・小）の API のモデルの公開価格。実装時に調べ、出典と調べた日を `.env.example` に書く。
- ChatGPT のトークンが無いとき（`review-judge` などの中身が偽 LLM のとき）は、単価を設定しない（A は 0）。
- 審査官の呼び出しの A の額は、`review` の `judge_cost_usd` から取る（5.3 節）。
- `chatgpt/` のモデルでも、`model_info` に単価を設定すれば LiteLLM が利用料を計算する（ルーターが単価を登録し、利用料の計算がそれを使う。`chatgpt/` だけの分岐は無い）。前提は、ChatGPT 側がトークン数を返すこと。

### 7.2 B（按分）

- 月 m は日本時間の月。
- 請求の単位 k、月 m について: `r = F(k, m) / C(k, m)`、利用者 u の按分額 = `A(u, k, m) × r`。`C` は、その単位に当てはまるモデルの `usage_daily` の `cost_usd` の合計（`category` が `request` と `review` の両方、「利用者なし」を含む）。
- `F` は請求の単位の通貨で入っているので、`r` は「A の 1 米ドルあたりの、その通貨の額」になり、按分額はその通貨で出る。
- 円への換算: 通貨が `JPY` ならそのまま。`USD` ならその月の換算のレートを掛け、1 円未満を切り捨てる（円でも合計が合うよう、端数は按分と同じく最大の利用者に足す）。レートが未入力なら円の列は空にし、`fx_status: missing` にする。
- 「利用者なし」は 1 人の利用者と同じように按分の対象にし、行として出す（利用者には付けない）。
- 端数: 利用者ごとに通貨の最小単位（米ドルはセント、円は 1 円）未満を切り捨て、合計と `F` の差を、A の額が最も大きい利用者に足す。
- `C = 0` のときは、按分せず「未配分」の行に `F` を出す。
- `F` が未入力のときは B を出さない（`status: no_fee`）。`kind: subscription` で当月の `F` が入っていれば、当月の途中でも同じ計算で見込みを出す（`status: estimate`）。月が締まり `F` が入っていれば `status: final`。`kind: invoice` は請求書が届いてから `F` を入れるので、入れるまでは `no_fee`。
- どの請求の単位にも当てはまらないモデルは、精算の「対象外」の行（`row_kind: uncontracted`）に A だけを出す。

### 7.3 請求の単位の定義と換算のレート

**請求の単位**（`billing/contracts/<時刻>-<pod>.json`。最も新しいファイルが今の定義）:

```json
{
  "schema": 1,
  "contracts": [
    {"id": "chatgpt-plus", "name": "ChatGPT Plus", "kind": "subscription", "currency": "USD",
     "models": ["<Codex 用の model_name>", "review-judge"], "fees": {"2026-10": 20.0}},
    {"id": "claude-max", "name": "Claude Max", "kind": "subscription", "currency": "USD",
     "models": ["anthropic/*", "claude-*"], "fees": {"2026-10": 100.0}}
  ]
}
```

- `kind` は `subscription`（定額。月額を先に入れる）か `invoice`（従量課金の請求書。請求書の金額を月ごとに後から入れる）。
- `currency` は `USD` か `JPY`。
- `models` は完全一致か、末尾に `*` を付けた前方一致。記録の `model_group` と `model` の**どちらか**に当てはまれば、その単位に属する（Claude のように設定が `anthropic/*` で、記録のモデル名が版ごとに変わるものも拾えるように）。
- 1 つのモデルが 2 つの請求の単位に当てはまる指定は、保存を断る。
- 初期値は `.env` の `LAB_CONTRACTS`（定義のファイルが 1 つも無いときだけ書く）。以後は管理者の画面で編集する。

**換算のレート**（`billing/fx_rates/<時刻>-<pod>.json`。最も新しいファイルが今の値）:

```json
{"schema": 1, "usd_jpy": {"2026-10": 150.0}}
```

- 管理者が検索アプリで入れる。どのレート（月末の TTM など）を使うかは社内の規程に従う。初期値は `.env` の `LAB_FX_RATES`。

**同時に編集されたとき**: 編集は上書きではなく、毎回新しいファイルを足す（追記だけなので、2 台の検索アプリが同時に書いても片方が消えることはない）。画面は編集の元にした版の名前（`base_version`）を送り、書いた後に「自分の書いたファイルの 1 つ前が `base_version` か」を確かめる。違えば、ほかの人が間に編集したことを表示し、管理操作の記録には両方が残る。編集のたびに `admin` の記録を書く。

### 7.4 `billing/settlement/month=YYYY-MM/part-0.parquet`

| 列 | 内容 |
|---|---|
| `row_kind` | `user`（利用者）/ `no_user`（利用者なし）/ `unallocated`（未配分）/ `uncontracted`（対象外のモデル） |
| `contract_id` | 請求の単位（`uncontracted` の行は空） |
| `user_id` / `user_email` | 利用者（`user` の行だけ） |
| `cost_a_request` / `cost_a_review` | A の額（要求の分、審査の分） |
| `cost_b` | 按分額 |
| `rate` | 配分率 `r` |
| `fee` / `currency` | 実費 `F` と、その通貨 |
| `fx_rate` / `cost_b_jpy` / `cost_a_jpy` | 換算のレートと、円に換算した按分額・A の額（参考） |
| `fx_status` | `ok` / `missing` / `not_needed`（円の請求の単位） |
| `status` | `estimate` / `final` / `no_fee` |
| `contracts_version` / `fx_version` | 計算に使った請求の単位の定義とレートの版 |
| `computed_at` | 計算した時刻 |

## 10. 障害の試験の作り（`./lab test-failover`）

- 負荷: 構築ツールの中で、Python のスレッドで偽 LLM（`fake-tools`）に 1 秒 20 件を送り続ける。要求ごとに、時刻、結果、応答の見出しの `x-litellm-call-id` を記録する。
- 場面ごとの起こし方:

| 場面 | 起こし方 | primary の見つけ方 |
|---|---|---|
| `pg-switchover` | `kubectl cnpg promote litellm-pg <standby>` | `Cluster` の `status.currentPrimary` |
| `pg-pod` | primary の Pod を `kubectl delete pod` | 同上 |
| `pg-node` | primary のノードを `docker stop`、120 秒後に `docker start` | Pod の `spec.nodeName` |
| `valkey-pod` | primary の Pod を `kubectl delete pod` | Sentinel に `get-master-addr-by-name` |
| `valkey-node` | primary のノードを `docker stop`、120 秒後に `docker start` | 同上 |

- ノードを止める場面では、k3d の server ノード（`k3d-litellm-server-0`。Kubernetes の制御部分と RustFS が載っている）は止めない。primary が server ノードにあれば、先に agent ノードの台へ切り替え（PostgreSQL は `kubectl cnpg promote`、Valkey は `SENTINEL FAILOVER`）、落ち着いてから止める。
- 出す結果: 失敗した要求の数、最初の失敗から最後の失敗までの時間、LiteLLM の Pod の再起動の回数、切り替え後の primary の数（Valkey は Sentinel の 3 台の答えが一致するか）、監査ログの欠け（送った `x-litellm-call-id` と `raw/meta` の `call_id` の差。2.2 節のつなぎ方で読む）。
- 監査ログの欠けの判定: Pod を消す場面と計画的な切り替えでは 0 件。ノードを止める場面では、止めたノードにあった LiteLLM の Pod の、書き出し前の記録（最大 `LAB_AUDIT_FLUSH_SECONDS` 秒分）が失われうるので、欠けた要求がすべてその Pod の、止める直前の 10 秒に入っていれば合格とする。
- 結果は `.build/failover-<日時>.json` に保存し、仕様の合格の条件で判定する。

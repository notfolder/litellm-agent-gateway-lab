作成: 2026-10-26
状態: 実装済み（単体試験とテンプレートの検査まで。AWS への配備と試験は、EC2 3 台の環境そのものの配備（`.history/2026-10-25-EC2三台構成/`）の後）

## 0. 背景と決定事項

### 0.1 背景

EC2 3 台の環境の実装が終わった後、ユーザーから「この構成で Kubernetes のマイナーバージョンアップを無停止でできるか」と問われ、調査した（2026-10-26）。結論は次のとおり。

- **構成としては耐えられる。** k3s の server 3 台（組み込み etcd）は 1 台を抜いても多数決を保ち、PostgreSQL（CloudNativePG 3 台）、Valkey と Sentinel（各 3 台）、Traefik（2）、registry（2）、オペレーター（2）はどれも 1 台欠けに耐える。k3s の公開手順も「server を 1 台ずつ」で、Kubernetes の版の差の規則（apiserver 同士は 1 つ違いまで。kubelet は apiserver より新しくしない）に収まる。
- **実装には手順が無く、今のやり方では止まる。** k3s の版が user data に埋め込まれていて、変えて `./lab up` を流すと CloudFormation が 3 台を同時に再起動する（`UserData` の更新は「Some interruptions」）。しかも初期化スクリプトは 2 回目は抜けるので、版は変わらない。k3s の起動引数をコマンドラインで渡しているので、インストールスクリプトを再実行すると引数が消える。cordon・drain・順送りの手順も無い。
- **関連して、より重い落とし穴が見つかった。** AMI を「最新」を指す SSM の公開パラメータで解いているため、新しい AMI が出た後に `./lab up` を流すと、`ImageId` の更新が「Replacement」で 3 台が同時に置き換えられ、EBS（etcd と `local-path` の DB）が消える。版上げと無関係に、配備後の 2 回目以降の `./lab up` で起きうる。

### 0.2 決定事項（2026-10-26、ユーザーの回答）

| 項目 | 決定 |
|---|---|
| AMI の固定 | **今すぐ直す**（回答 1A）。配備後の `./lab up` でデータが消えうる不具合なので、配備の前に潰す |
| 版上げの手順 | **全部今実装する**（回答 2C。「今書いておいて、試せるようになったらすぐ試せるようにしたい」）。配備できない状態で書くので、drain の挙動や転送の張り直しは配備後の試験で確かめる |
| 無停止の意味 | **数秒〜数十秒の接続の切れ直しを許す。** 処理中の長い応答（ストリーミング）は、その Pod が載った台の番で切れる。Elastic IP が移る瞬間に張ってあった TCP 接続も切れる。これを「無停止」と呼ぶ（0.1 の調査結果をユーザーに報告し、2C の回答で進めた） |
| Mac と EKS 版 | Mac の k3d は版を変えると作り直し（`./lab rebuild`）のまま。EKS 版は EKS の版の更新（CDK）のまま。手順は `aws-ec2` だけ |

### 0.3 既存の仕様から変える方針

- EC2 3 台の環境の変更仕様書 5 章「構築ツールの要件」に、**k3s の版上げの要件**（2 章）を足す。
- 既存の仕様書 9.3「無停止のバージョンアップ」の観点に、**Kubernetes そのものの版上げ**を足す（今までは LiteLLM の版上げだけだった）。

| 区分 | 内容 |
|---|---|
| 変える | `aws-ec2` の CloudFormation の nodes スタック（AMI の受け方、k3s の版の受け方）、EC2 の初期化スクリプト（引数の置き方、版の読み方）、構築ツール（`./lab upgrade-k8s` の追加、`./lab cluster` の版の食い違いの検知、ポート転送の張り直し）、LiteLLM の PodDisruptionBudget（3 環境に共通） |

## 2. 要件

### 2.1 k3s（Kubernetes）の版上げ

| # | 要件 |
|---|---|
| R1 | `./lab upgrade-k8s <版>` で、EC2 3 台の k3s を **1 台ずつ** 上げられる。上げている間、入口（`https://<ホスト名>`）への要求が止まらない（0.2 の「無停止の意味」）。 |
| R2 | **マイナー版は 1 つずつ**しか上げられない。飛ばす指示と、下げる指示は止める（Kubernetes の版の差の規則）。同じマイナー版の中のパッチの更新はできる。 |
| R3 | 上げる前に **etcd のスナップショット**を取る（戻すときの控え）。 |
| R4 | 1 台を上げる手順は「Pod を他の台へ追い出す → k3s を新しい版で再起動する → その台が新しい版で Ready になるのを待つ → 追い出しを解く → DB・Redis・LiteLLM がそろうのを待つ」。次の台はその後。 |
| R5 | **Elastic IP を持つ台は最後**に上げる（入口の移動を 1 回にする）。 |
| R6 | 構築ツールの k3s の API への接続（Session Manager のポート転送）は、上げる台とは別の台に張り直してから、その台を上げる。 |
| R7 | 途中で止まっても、もう一度流せば**上げ終わった台を飛ばして続きから**進む。 |
| R8 | 上げ終わったら、**作り直した台も新しい版で参加する**（版の置き場を更新する）。 |
| R9 | `./lab up`（`./lab cluster`）は **版を変えない**。配備済みの版とコードの版が食い違っていたら、`./lab upgrade-k8s` で上げるか、コードの版を合わせるかを案内して止める。 |
| R10 | `--measure` を付けると、上げている間に偽 LLM への要求を流し続け、失敗の数と失敗が散らばった時間を報告する（障害の試験と同じ測り方）。配備後の試験で「無停止」を実測するため。 |
| R11 | 版を上げる操作で、**CloudFormation の nodes スタックに差分が出ない**（3 台の同時再起動を起こさない）。 |

### 2.2 AMI の固定

| # | 要件 |
|---|---|
| R12 | 配備済みの環境に `./lab up` を流しても、**新しい AMI が出たことを理由に EC2 が置き換えられない**。 |
| R13 | 初回の配備では、今までどおり AL2023 arm64 の最新の AMI を使う（人が AMI ID を調べない）。 |
| R14 | `./lab down` → `./lab up` では新しい AMI になってよい（作り直しなので）。 |

### 2.3 LiteLLM の追い出しの上限

| # | 要件 |
|---|---|
| R15 | ノードの drain で LiteLLM の Pod が **同時に 2 つ以上消えない**（PodDisruptionBudget。HPA が同じ台に 2 つ置いたときの守り）。親ブランチ `feature/aws-target` が Helm チャートの値（`litellm/values.yaml` の `pdb`、`maxUnavailable: 1`）で 3 環境に足したものを使い、この変更では別に付けない（同じ Pod に PDB が 2 つ当たると Kubernetes は追い出しを拒み、drain が止まる）。 |

## 3. 無停止の範囲と、止まるもの

| 層 | 1 台を上げている間に起きること | 利用者から見えるか |
|---|---|---|
| k3s の制御部分 | 残り 2 台で多数決を保つ。上げる台の apiserver が数十秒止まる | 見えない（構築ツールは別の台に転送している） |
| PostgreSQL | primary の台なら先に切り替わる（Pooler 越しでは失敗 0 件の実測あり）。replica は台が戻るまで待つ | 見えない（切り替えの間、Pooler が要求を待たせる） |
| Valkey と Sentinel | primary の台なら Sentinel が 5 秒で検知して昇格 | 見えない（LiteLLM は Sentinel 経由で追従） |
| LiteLLM | その台の Pod が消え、残りが受ける。処理中の要求（ストリーミングを含む）は切れる | **その台の処理中の要求だけ失敗する** |
| 入口（Traefik、Elastic IP） | Elastic IP の台の番で、6 秒ほどで別の台に移る。張ってあった TCP 接続は切れる | **数秒の接続の切れ直し**（1 回。最後の台） |
| registry、cert-manager、オペレーター | 2 つのうち 1 つが消え、残りが続く | 見えない |
| Gmail の MCP（1 Pod） | その台の番で短く止まる | その間だけ Gmail のツールが使えない |

## 4. 検証項目（仕様書 9.3 への追加。配備後）

| 項目 | 合格の目安 |
|---|---|
| `./lab upgrade-k8s <次のマイナー版> --measure` | 3 台とも新しい版で Ready。要求の失敗は、各台の番で数件以内、失敗が散らばった幅が台ごとに 30 秒以内。LiteLLM の Pod の繰り返し再起動が無い。PostgreSQL と Valkey の primary が 1 台 |
| 同じマイナー版のパッチの更新 | 同上 |
| マイナー版を飛ばす指示、下げる指示 | 分かるメッセージで止まる |
| 途中で止めて（Ctrl-C）もう一度流す | 上げ終わった台を飛ばし、残りだけ上げる |
| 上げた後に `./lab up` | 版の食い違いで止まり、`K3S_IMAGE` を合わせる案内が出る。合わせたら通る（CloudFormation に差分が出ない） |
| 上げた後に 1 台を作り直す（インスタンスを消して `./lab cluster`） | 新しい版で参加する |
| 配備済みの環境に `./lab up`（AMI の固定） | CloudFormation の nodes スタックに差分が出ない（新しい AMI が出た後でも） |
| Mac で `./lab up` | 何も変わらない（PDB `litellm` は親ブランチの変更で付く） |

## 5. リスク・注意事項

- **k3s の再起動で Pod のコンテナは動き続ける**（k3s の文書）が、drain で追い出すので、その台の Pod は消える。drain しない選択（短い API の途切れだけで済ます）もあるが、CloudNativePG の primary を切り替えずに kubelet を止めるより、drain で計画的に切り替える方が安全と判断した。
- **k3s の起動引数を設定ファイルに移した**ので、インストールスクリプトの再実行で引数が消えない。参加先（`server:`）と `cluster-init` も設定ファイルに書くが、etcd のデータがある台の再起動では無視される（k3s の挙動。配備で確かめる）。
- **k3s 同梱の Traefik・CoreDNS・ServiceLB は k3s の版と一緒に上がる。** Traefik のチャートの値（`traefik-config-ec2.yaml`）の形が新しいチャートで変わっていないかを、上げる前に k3s のリリースノートで確かめる。
- **CloudNativePG のオペレーターと Barman Cloud Plugin が新しい Kubernetes の版に対応しているか**を、上げる前に確かめる（対応表はオペレーターの文書にある）。
- **転送の張り直し**は Session Manager のセッションを一度切る。構築ツールが持つ接続はそれだけなので影響は無い。
- **AMI の固定**は「置き換えを起こさない」ための守りであり、AMI を新しくする手順は別に要る（対象外。BACKLOG）。

## 1. Traefik の更新の仕方（R1。`k8s/traefik-config-vm.yaml`）

`valuesContent` に次を足す。チャート 40 と 41 で鍵は同じ（`updateStrategy.rollingUpdate.maxUnavailable` / `maxSurge`）。

```yaml
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 0
```

- 古い Pod を止めてから同じ台に新しい Pod を置くので、hostPort の取り合いが起きない。止まっている間はその台の 80 / 443 が応答せず、内部ロードバランサの
  ヘルスチェック（TCP 80）がその台を外す。外れるまでの要求は失敗しうる（台を 1 台止める場面と同じ形）。
- Mac の `k8s/traefik-config.yaml` は変えない（Deployment で hostPort を使わず、既定の「先に足す」で入れ替わる）。

## 2. チャートの版ごとの鍵（R2）

### 2.1 鍵の違い（traefik-helm-chart の Changelog 41.0.0 の Breaking changes と、40.1.0 / 41.4.0 の `values.schema.json`）

| 項目 | チャート 40（k3s 1.36） | チャート 41（k3s 1.37） |
|---|---|---|
| アクセスログ | `logs.access` | `accessLog` |
| 一般のログ | `logs.general` | `log` |
| 項目の既定 | `fields.defaultmode`、`fields.headers.defaultmode` | `fields.defaultMode`、`fields.headers.defaultMode` |

どちらのチャートも、知らない鍵を最上位に置くことを定義で認めていない（`additionalProperties: false`）ので、両方の鍵を書く形にはしない。

### 2.2 当て方

- `k8s/traefik-config.yaml` と `k8s/traefik-config-vm.yaml` は、今のコードの k3s（v1.36.5、チャート 40）の形のまま書く。
- `render.traefik_chart_major(chart)`: HelmChart `kube-system/traefik` の `spec.chart`（例 `https://%{KUBERNETES_API}%/static/charts/traefik-41.4.2+up41.4.0.tgz`）
  から主版（41）を取り出す。読めなければ `None`。
- `render.traefik_config(text, major)`: HelmChartConfig の YAML を受け取り、主版が 41 以上なら `valuesContent` の鍵を 2.1 の表のとおり書き換えて返す。
  40 以下か `None` なら書き換えない。
- `stages.apply_traefik_config(path)`: HelmChart `traefik` が現れるのを待ち（k3s が起動時に作る。最長 180 秒）、`spec.chart` を読み、`render.traefik_config` で
  書き換えた定義を `kapply`（差分があるときだけ apply）する。使ったチャートの版を表示する。Mac の `cluster` 段階と VM の `cluster` 段階は、
  今の `kapply(files=[...traefik-config*.yaml])` をこれに替える。
- `ops.upgrade_k8s`: 台ごとに「Ready と版を待つ → uncordon」の後に `stages.apply_traefik_config` を呼び、その後の `rollout status ds/traefik` を待つ。
  全台を上げた後にもう一度呼び、`vm.wait_traefik`（全台が新しい定義で ready）を待つ（どの台の k3s が HelmChart を書き換えたかによらず、最後は新しいチャートに合う）。

## 3. 止まっている台の確かめ（R3）

- `clouds.Node` に `state`（小文字。AWS は `State.Name`、GCP は `status`）を足す。`aws_ec2._to_node` と `gcp._to_node` が埋める。
- `clouds.STOPPED_STATES = {"stopping", "stopped", "terminated", "suspending", "suspended"}`。
- `clouds.require_running(nodes, start_command)`: `state` が `STOPPED_STATES` の台があれば `LabError` を出す。メッセージは
  「止まっている台があります: node2（i-…、stopped）。./lab up は止まった台を起こしません。台を起こしてから流し直してください（managed: <起こすコマンド>。
  provided は用意する側に依頼）。クラスタは残りの台で動き続けます」。
- 各クラウドに `start_command(env, node)`（AWS: `aws ec2 start-instances --instance-ids <id>`、GCP: `gcloud compute instances start <名前> --zone <ゾーン>`）を足し、
  `FUNCTIONS` に入れる。
- 呼ぶところ:
  - `aws_ec2.ensure_nodes`: `instance_running` を待つ前（managed。止まった台を待って時間切れにしない）。
  - `stages` の VM の `cluster` 段階: `vm.load_infra` の直後（managed と provided。GCP の managed は台の作成で RUNNING を待たないので、ここで捕まえる）。
- `./lab down`、障害の試験、`upgrade-k8s` は `require_running` を呼ばない（止まった台があっても消せる、試験で止めた台を扱える）。

## 6. 版上げの途中のチャートの変化を見張る（R6。`stages.TraefikChartWatch`、`ops.upgrade_k8s`）

- k3s は上げた台が起動した時点で、同梱のチャート（HelmChart `kube-system/traefik` の `spec.chart`）を書き換える。helm-controller はすぐ古い鍵の設定のまま
  Traefik を入れ替えるので、`./lab` が台ごとの最後に当て直すまでの間（5 章の 1. で約 1.5 分）、アクセスログの指定が無い定義になる。
- `upgrade_k8s` は台を上げ始める前に見張りを始め、3 秒ごとに `spec.chart` を読む。変わったらすぐ `apply_traefik_config` で新しいチャートの鍵で当て直す。
  台ごとの当て直しと、最後の当て直しと待ちは残す（見張りが失敗しても最後には必ず新しい鍵になる）。
- 結果に `traefik_chart_changes`（見張りが見たチャートの変化）を入れる。

## 7. metrics-server を 2 台にする（R7。`stages.ensure_metrics_server`、`render.metrics_server_patch` / `metrics_server_pdb`）

- k3s に同梱の定義（`manifests/metrics-server/metrics-server-deployment.yaml`）は台数も散らす指定も書かない。CoreDNS（`ensure_coredns`）と同じく、同梱の定義に無い
  項目だけを足す: 台数 2、台ごとに 1 つずつ散らす指定（`kubernetes.io/hostname`、`maxSkew: 1`、`DoNotSchedule`、`nodeTaintsPolicy: Honor`）。
  k3s が定義を当て直しても、定義に無い項目は残る（版上げの後に確かめる）。
- PDB `kube-system/metrics-server`（`maxUnavailable: 1`）を付ける。
- `./lab up` の `cluster` 段階（Mac の k3d と VM）で、CoreDNS の後に流す。k3s を止めて同梱の物を別に入れる形は取らない（部品の数が増えず、CoreDNS と同じ扱いで済むため）。

## 8. LiteLLM の PDB（R8。`litellm/values.yaml`）

- `pdb.maxUnavailable` を `"25%"` にする。PDB の割合は切り上げなので、2〜4 台なら 1、5〜8 台なら 2。
- 効く範囲: 起動中の Pod が 1 つ（6〜8 台のとき）なら、退避を断られずに進む。自動の台数調整で一度に 2 つ以上増えて起動中の間は、25% でも断られる
  （例: 6 台のうち 4 台が起動中なら、許される 2 を超える）。その間に追い出すと LiteLLM の受け手が足りなくなるので、待つのは PDB の守りのとおり。

## 9. `worker-node` で LiteLLM が載った足す台を止める（R9。`failover._put_litellm_on_worker`）

- 場面の前（負荷を流す前）に、足す台に LiteLLM の Pod（終了中を除く）があるか見る。無ければ `rollout restart deploy/litellm` で入れ替え、散らす指定で
  足す台にも置かれるのを待つ（最大 3 回）。それでも無ければ `LabError` で止める。前は載っていなくても 1 台目の足す台を止めていた（2026-11-04 の AWS）。

## 10. 80 番から 443 番への転送（R5。`k8s/traefik-config-vm.yaml`）

- チャート 39 から転送の鍵の位置は `ports.web.http.redirections`。前の `ports.web.redirections` はチャート 39〜41 では黙って無視され、80 番は 404 だった。
  チャート 39 / 40 / 41 の `values.yaml` で位置が同じことを確かめた（38 までは `ports.web.redirections`）。

  最後の台の後（全台の Traefik の待ち）は「後」の区間にする。結果の `per_node` に入れる。

## 13. AMI を新しくする（`./lab upgrade-ami [--measure]`。`ops.upgrade_ami`、`vm.forget_node` / `init_node`、`aws_ec2.replace_instance` / `latest_ami` / `node_image`）

- 新しくする先は、流した時点の Canonical の Ubuntu 24.04 の最新（CPU の種類は `LAB_EC2_INSTANCE_TYPE`。11 章）。`aws-ec2` の managed だけ。
  provided は台を作り直さず、用意する側に頼む手順（1 台ずつ drain → 同じ内部 IP で作り直してもらう → `./lab up`）をメッセージで出して止まる。
- 順は版上げと同じ（今の 3 台が先、SSH の転送先が 3 台の最後、足す台が後）。新しい AMI でない台と、クラスタにノードが無い台（前の実行が途中で止まった）が対象。
- 前に server の台で etcd のスナップショットを取る（`snapshot_node`）。
- 台ごと:
  1. 転送先を別の台へ → drain。
  2. `vm.forget_node`: その台のディスクにある PVC（local-path の PV の nodeAffinity がその台）と、それを使う Pod を消し、ノードを消す。
     ノードを消すと k3s がその台の etcd のメンバーとノードのパスワード（`<名前>.node-password.k3s`）を外す（k3s の記録「Removing etcd member from cluster
     due to node delete」）ので、同じ名前（同じ内部 IP → 同じホスト名）の新しい台が参加できる。Zabbix のホストも消す（自動登録で作り直される）。
  3. `aws_ec2.replace_instance`: インスタンスを消し、同じ番号・同じ内部 IP で新しい AMI から作り、内部 NLB のターゲットに戻す。`.env` の
     `LAB_VM_NODES` / `LAB_VM_WORKER_NODES` の識別子を置き換える（順は保つ）。
  4. `vm.init_node`: その台だけを SSH で初期化する（生きている server の台に参加する。1 番を作り直しても新しいクラスタは起こさない）。
  5. Ready → 入口の印 → PostgreSQL 3 台と Valkey 3 台（CloudNativePG は消えた PVC の代わりのレプリカを作り、Valkey は StatefulSet が PVC を作り直して
     primary から写す）→ Traefik の全台。
- 途中で止まっても流し直せば続きから進む: 新しい AMI でない台で、クラスタにノードがあれば 1 から、無ければ 3 から。新しい AMI の台でクラスタにノードが
  無ければ 4 から。クラスタに無い台があるときは、最初の「PostgreSQL と Valkey がそろうのを待つ」を飛ばし（欠けた台が戻るまでそろわない）、その台から始める。
- `vm/node-init.sh` の k3s のインストールは、取得の一時的な失敗で止まらないよう 15 秒おきに 3 回までやり直す（`install_k3s`）。
- `--measure` は `upgrade-k8s` と同じ（12 章の台ごとの失敗も出す）。

## 14. Zabbix への LiteLLM の指標（`zabbix_monitors.litellm_specs`、`render` の `litellm_settings`）

- LiteLLM の `callbacks` に `prometheus` を足す（v1.104.2 の無償版で `PrometheusLogger` に有料版の確かめは無い）。`/metrics` は既定で鍵が要るので
  `require_auth_for_metrics_endpoint: false` にする。外からは Traefik が `/metrics` を踏み台だけに絞る（`render.ADMIN_PATH_PREFIXES`）。
- 指標は Pod ごとに別に数えられるので、入口からは読まない。ホスト `litellm-lab-k8s`（クラスタの中の zabbix-proxy が集める）に:
  - HTTP アイテム `lab.litellm.pods`（Kubernetes の API で `litellm-lab` の `app.kubernetes.io/name=litellm` の Pod の一覧）と、それを元にした発見ルール
    `lab.litellm.pods.discovery`（Running で IP のある Pod。`{#POD}`、`{#PODIP}`）。
  - プロトタイプ: `lab.litellm.metrics[{#POD}]`（`http://{#PODIP}:4000/metrics` を 1 分ごと。履歴は残さない）と、従属アイテム 5 つ（要求の数、失敗した要求の数、
    待ち時間の合計と数、LLM の送り先の失敗の数）。どれも数え上げの合計（Prometheus の前処理）→ 毎秒の変化。まだ出ていない指標は 0。
    Pod の入れ替えで数え直しが起きても、毎秒の変化は小さくなった値を捨てる。
  - 計算アイテム: 5 つの全 Pod の合計（`sum(last_foreach(.../lab.litellm.<名前>.rate[*]))`）、失敗した要求の割合（%）、平均の待ち時間（秒）。0 で割らないよう
    分母に 0.0001 を足す。計算アイテムはプロトタイプを足すので、発見ルールの後に作る（`items_after`）。
  - 警報: 「失敗した要求の割合が 5 分続けて 5% を超えた」（警告）、「LLM の送り先の失敗が 5 分続いている」（警告）。

試験の中で見つけて直した不具合:

1. 版上げの前の etcd のスナップショットを上げる順の最後の台で取っていて、足す台がある構成では足す台（etcd が無い）で失敗した → server の台で取る（`ops.snapshot_node`）
2. 上げた後の `./lab up` の案内が、配備済みの方が新しいときに「upgrade-k8s <古い版>」と出ていた → 向きで案内を変える（`vm.version_mismatch_message`）
3. 作り直した台の k3s の取得が一時的に失敗し（中継越しの GitHub。手で流し直すと 200）、台がクラスタから外れたまま止まった → 15 秒おきに 3 回までやり直す（`install_k3s`）
4. `upgrade-ami` を「古い台を消した後・新しい台が参加する前」で止めると、流し直しで台の名前が見つからず進めなかった → クラスタに無い台も対象にし、AMI が新しければ参加から続ける
5. その続きの最初に「PostgreSQL と Valkey がそろう」を待ち、欠けた台が戻るまでそろわず 600 秒の時間切れになるところだった → クラスタに無い台があるときは最初の待ちを飛ばす
6. LiteLLM v1.104.2 の `/metrics` は既定で鍵を求め、Zabbix が 401 になった → `require_auth_for_metrics_endpoint: false`（6A）
7. managed の中継の VM（踏み台）の古い鍵が `known_hosts` の `bastion` に残り、provided の踏み台で SSH が失敗したのを台の鍵の変化と取り違え、台の行を消し続けて進まなかった → ssh の「Host key for <名前> has changed」の相手の行を消す。managed の `./lab down` は踏み台の鍵を忘れる

分かったこと:

- パッチの更新でも同梱の Traefik のチャートが変わる（40.1.5 → 40.1.7）。見張りがあると Traefik の入れ替えはチャートの変化ごとに 1 回で済む（見張る前の 11/08 朝は 1 回の変化で 2 回入れ替わった）。
- 版上げの台ごとの失敗の幅は 1 台目と 3 台目で約 72 秒（`.history/2026-10-26-k3s版上げ/変更仕様書.md` 4 章の「台ごとに 30 秒以内」を超える）。`docs/spec.md` は「数と幅を記録する」で、合否の目安は置いていない。
- 担当部署の役で置いた明示プロキシ（apt の mitmproxy 8.1.1）は既定で大きな応答をためてから流し、台の初期化が 1 台 7 分、PostgreSQL のイメージの取得が時間切れになった（`stream_large_bodies=1m` で毎秒 10.8 MB。`./lab` の不具合ではない）。本番の Zscaler でも、大きなダウンロード（k3s、コンテナのイメージ）が通る速さを先に確かめる。
- managed から provided に入口の IP が変わると、Mac の名前解決が古い IP を覚えている間（約 5 分）`./lab` が待つ。

# 変更仕様書: 台が 1 台止まったときに全体を止める「1 台だけの部品」を冗長にする

作成: 2026-11-05
状態: 実装中
この文書の役割: **何を満たすか（要件）と、何を決めたか（決定）**。どう作るかは `変更設計書.md`

## 0. 背景と決定事項

### 0.1 背景

2026-11-04 の `aws-ec2` の配備で、障害の試験 `valkey-node` が回復まで 179.5 秒（目安 120 秒）になった。
Mac と AWS で切り分けた結果（`.history/2026-10-31-内部LBとVM側の防御とZabbix/変更設計書.md` 15.2.1〜15.2.3 節）:

- k3s に同梱の CoreDNS（名前解決）は 1 台だけ。載った台が止まると名前解決が止まり、LiteLLM が DB に届かないと判断して全台が外れる（AWS の実験 1: 回復 102.3 秒。CoreDNS を 3 台にした実験 2: 23.0 秒）。
- CloudNativePG の Barman Cloud Plugin（`barman-cloud`）は 1 台だけ。載った台が止まると CloudNativePG が PostgreSQL の切り替えを始めず、プラグインが別の台で作り直されるまで約 60 秒遅れる（実験 3）。
- 試験の偽 LLM が 1 台だけだった件は直した（`k8s/fake-llm.yaml`、2026-11-05）。

### 0.2 決定事項（2026-11-05、ユーザーの回答）

| # | 問い | 決定 |
|---|---|---|
| 1 | CoreDNS | **`./lab up` のたびに、k3s に同梱の CoreDNS を 3 台にそろえる（台ごとに散らす）**（1A）。同梱を止めて自前で入れる案は採らない |
| 2 | Barman Cloud Plugin | **2 台にして台ごとに散らし、止まった台からは 30 秒で移す**（2A。動くのは 1 台、もう 1 台は待機） |
| 3 | LiteLLM の readiness | **今のまま（DB を見る）**（3A）。DB に依存させない形は、DB の切り替えの間に覚えていないキーが 401（認証の失敗）になり、クライアントが再試行しないため採らない |
| 4 | 確認 | 変更仕様書・変更設計書を書いて実装し、AWS（`aws-ec2`）で `valkey-node`・`pg-node`・`entry-node` を流して確かめる（4A） |

## 1. 要件

- R1. k3s を使う環境（Mac の k3d、`aws-ec2`、`gcp-vm`）で、CoreDNS が 3 台動き、別々の台に載る。`./lab up` を流すたびにそうなる。
- R2. `aws-ec2` / `gcp-vm` で、Barman Cloud Plugin が 2 台動き、別々の台に載る。止まった台からは 30 秒で別の台へ移る。
- R3. 台を 1 台止めても、名前解決と PostgreSQL の切り替えが、止めた台に載った CoreDNS や Barman Cloud Plugin を待たない。
- R4. `./lab up` を 2 回流したとき、2 回目で何も変わらない（冪等）。

## 2. 範囲

- 対象: CoreDNS（k3s を使う 3 環境）、Barman Cloud Plugin（VM の 2 環境）。
- 対象外: EKS 版（`LAB_TARGET=aws`。CoreDNS は EKS が管理し、CloudNativePG を使わない）。LiteLLM の readiness（決定 3）。
  ほかの 1 台だけの部品（metrics-server、local-path-provisioner）は要求の経路に無いので変えない。
- Mac の Barman Cloud Plugin は 1 台のまま（オペレーター類と同じく、障害の試験で止めない server の台に固定しているため）。

## 3. 受け入れの確認

- AWS（`aws-ec2`）で `test-failover` の `valkey-node`・`pg-node`・`entry-node` が目安（120 秒）以内に回復する。
- CoreDNS が 3 台、Barman Cloud Plugin が 2 台、それぞれ別の台に載っている。
- `test-smoke` と `test-idempotency` が通る。

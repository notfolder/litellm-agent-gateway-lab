## 1. CoreDNS（要件 R1）

- k3s に同梱の CoreDNS（`/var/lib/rancher/k3s/server/manifests/coredns.yaml`、k3s v1.36.5+k3s1）は `replicas` を書かず、
  `topologySpreadConstraints`（`kubernetes.io/hostname`、`DoNotSchedule`、maxSkew 1）を持つ。k3s が定義を適用し直しても、
  台数は書き戻されない（2026-11-05 の AWS で、`kubectl scale` した 3 台が台の再起動の後も残った）。
- `stages.ensure_coredns()` が `kube-system/coredns` の台数を `render.COREDNS_REPLICAS`（3）にそろえ、`rollout status` を待つ。
  台数が同じなら何もしない（冪等）。
- 呼ぶ場所: Mac の k3d（`stages.cluster` の全ノードの Ready の直後）と VM の環境（`stages._cluster_vm` の全ノードの Ready の直後）。
  EKS 版は呼ばない。
- 散らし方は同梱の定義のまま（台ごとに必ず散らす）。3 台の環境では 1 台ずつ載る。1 台が止まっている間は、作り直す Pod は置けずに
  待つが、残りの 2 台で名前解決は続く。

## 2. Barman Cloud Plugin（要件 R2）

- 取得したままの公式のマニフェストを `.build/barman-cloud-<版>.yaml` に置き、`render.barman_plugin_manifest(text, node_selector, replicas)`
  で毎回書き換えて `.build/barman-cloud-<版>-pinned.yaml` に書く（内容が変わったときだけ書き換える）。
  - 前からの処理（`render.pin_deployments`）: Deployment を server ノード（`CONTROL_PLANE`）に置く。
  - `replicas` が 2 以上のとき: `barman-cloud` の Deployment の `spec.replicas` をそろえ、`topologySpreadConstraints` を足す
    （`kubernetes.io/hostname`、`DoNotSchedule`、maxSkew 1、`nodeTaintsPolicy: Honor`、`labelSelector` は Deployment の selector）。
- `nodeTaintsPolicy: Honor` は、止まった台（`node.kubernetes.io/unreachable` などの taint）を散らす計算から外す。外さないと、
  止まった台の分が偏りとみなされ、作り直す Pod が置けない。Kubernetes 1.33 で GA。
- 台数は `stages.operators(replicas)` の引数（VM は 2、Mac は 1）。cert-manager と CloudNativePG のオペレーターと同じ値。
- プラグインはリーダーを 1 台選ぶ（`leaderelection`）。待機の 1 台は ready にならない（gRPC の口を開かない）。リーダーの台が止まると、
  待機の 1 台がリースを取ってから動く。
- 待機の 1 台は ready にならないので、Deployment の更新は `Recreate`（全台を止めてから作り直す）。1 台ずつ入れ替えると、古いリーダーが
  動いている間は新しい台が ready にならず先へ進めない。`./lab` の待ち方は `rollout status` ではなく「全台が新しい版で、1 台以上が ready」
  （2026-11-05 の AWS の配備で判明）。
- 止まった台からの退避（30 秒）は、VM の kube-apiserver の既定（`default-not-ready-toleration-seconds=30`、
  `default-unreachable-toleration-seconds=30`、`vm/node-init.sh`）がプラグインにも効く（公式のマニフェストに `tolerations` は無い）。

### 4.1 「LiteLLM は ready なのに失敗が続く」の調査（2026-11-05 14:59〜15:47、AWS。ユーザー回答 1A）

試験の負荷に要求ごとの記録（送った時刻、待った時間、失敗の中身）を足し（`failover.Sample`。判定は変えない）、LiteLLM の全 Pod の記録と
接続の状態を集めながら `valkey-node`（Valkey の primary と Pooler の 1 台の台を止め、PostgreSQL の primary は別の台）と `pg-node` を流した。
構築から片付けまでを 1 本の台本にし、最後に必ず `./lab down` を流した（15:44 に有料の資源 0 件）。

| 場面 | 結果 |
|---|---|
| valkey-node | 失敗 190/4,971 件、回復 71.9 秒（合格）。失敗は止めてから約 40 秒の入口の段階だけ |
| pg-node | 失敗 1,730/5,436 件、回復 131.8 秒（目安超過）。失敗は次の 3 段階 |

pg-node の失敗の段階（10 秒ごとの集計）:

1. 止めてから約 40 秒: 接続のリセット、TLS の握手の失敗、502、504。止めた台の Traefik（NLB のヘルスチェック 10 秒 × 2 回で外れる）と
   LiteLLM（台が NotReady になって外れる）に振られた分。
2. 次の約 50 秒: 503 `no available server`。PostgreSQL の切り替えの間、LiteLLM の全台が unready（readiness が DB を見る。決定 3）。
3. 次の約 40 秒: 接続のリセット（`Errno 54`）、TLS の途中切断、証明書の検証の失敗。LiteLLM は ready に戻っている。送り遅れが最大 13 秒で、
   溜まった要求が一度に流れた時間帯と重なる。試験の負荷は Mac → 踏み台の SSH の転送 → NLB を通るので、転送の側で切れたと推定する
   （本番の利用者は VPC の中から NLB に届くので、この経路を通らない）。証明書の検証の失敗が出た理由は未特定。

11/5 07:53 の valkey-node（229.5 秒）は記録が無く段階を分けられないが、同じく 3 の形が長く続いたと推定する。
本物の構成の停止は 1 と 2 で約 90 秒（目安 120 秒以内）。

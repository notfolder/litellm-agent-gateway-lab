# AWS の消し残しの片付けと ECS の down の直し、GCP のメールの確認

## 概要
プルリクエスト #10 のマージ後に main へ戻り、AWS の消し残し（Cloud Map の名前空間と月 0.5 ドルのホストゾーン）を消して `down` を直し（プルリクエスト #11）、GCP からのメール 4 通を確かめた。

## やったこと
- main に戻した: プルリクエスト #10（`feature/aws-ecs`）は 2026-11-22 にマージ済み。main を早送りし、ローカルの `feature/aws-ecs` を消した（GitHub 側のブランチは残っている）
- AWS の確認（全リージョン、読み取りだけ）: EC2・EBS・NAT・EIP・ELB・RDS は 0 件。東京で EKS・ECS・ElastiCache・EFS・VPC エンドポイント・ASG なども 0 件
  - 消し残し: Cloud Map の名前空間 `litellm-ecs.internal` と、それが作った非公開のホストゾーン（月 0.5 ドル。11/22 に 0.5 ドルが請求に出ていた）
  - 原因（CloudTrail）: 2026-11-21 22:15 の最初の作成の失敗で巻き戻したとき、CloudFormation が作り終わる前の名前空間を消そうとして `NamespaceNotFound` になり、22:16 に作り終わった名前空間がどのスタックにも属さず残った。前回の全削除の確認でも見落とした
  - 消した（ユーザー回答 1A）
- `ecs/ecs-lab.sh` の `down` の直し（ユーザー回答 2A、ブランチ `fix/ecs-down-orphan-namespace`、プルリクエスト #11）
  - スタックを消したあとに `<接頭辞>.internal` の名前空間が残っていれば消す
  - AWS で、既定の VPC に同じ名前の非公開の名前空間を作って `down` で消えることを確かめた（作ったホストゾーンは 12 時間以内に消したので無料）
  - 確かめる途中で、bash 3.2 が `$NS（` のように全角の文字の直前の変数を変数名の一部として読み `unbound variable` で止まることが分かった。足した箇所と、前からあった 1 か所（中継が戻らないときのメッセージ）を `${…}` で囲んだ
  - 単体テスト 122 本が通る。変更設計書（`.history/2026-11-21-ECS構成/変更設計書.md`）15.1 節に 2 件を足した
- GCP からのメール（4 通）
  - 11/18 請求先アカウントが基準額請求に移行: 対応は要らない
  - 11/25 Service Specific Terms の 17 条（GCP Access Tools、2027-01-01 から）: 読むだけ
  - 11/25 Workspace の API の利用枠の変更: 2027-02-01 から、AI エージェントが REST API を直接呼ぶと Standard の枠に制限される。検証のゲートウェイの自前の Workspace MCP サーバーは Gmail の REST API を呼ぶので当たる見込み。今のまま使う（ユーザー回答 2B。IDEAS.md に記録）
  - 10/26（既読）別のプロジェクトの API キーの公開の通知: 最初の報告で「キーはまだ有効」と誤って伝えた（キーの文字列からキーを引く命令は、消したキーでも結果を返す）。確かめ直すと、通知の約 1 時間後の 10/26 13:05 にキーは消されていて、漏れたキーで呼ぶと `API_KEY_INVALID` で拒否された。消した後に成功した呼び出しは 0 件。制限を付ける作業（ユーザー回答 1B）は要らなかった。Docker Hub のイメージにキーの文字列が残っている件は、別のリポジトリ（coding-agent）の作業なのでここには書かない
- 意図的に残したもの: ACM の証明書 3 枚と `litellm-lab-cert` スタック（無料）、`CDKToolkit` などの以前からの物、GitHub の `feature/aws-ecs` ブランチ

## 決定事項

- Gmail の MCP サーバーは自前のまま使う（2B）
- push とプルリクエストの作成は許可を得てから行った（コミットと push を 1 つのコマンドにしたら自動の判定に止められた）

作成: 2026-10-31

## 1. 用語と `.env`

| 名前 | 意味 |
|---|---|
| 今の 3 台（server） | `LAB_VM_NODES` の 3 台。k3s の server（etcd を持つ）。Kubernetes のラベル `node-role.kubernetes.io/control-plane=true` |
| 足す台（worker） | k3s の agent。Kubernetes のラベル `litellm-lab/role=worker`（k3s が参加のときに付ける） |
| 入口の印 | Kubernetes のラベル `litellm-lab/entry=true`。Traefik はこの印のある台にだけ立つ。`./lab` が付け外しする |

| 鍵 | 既定 | 意味 |
|---|---|---|
| `LAB_VM_WORKERS` | `0` | managed: 足す台の数。`./lab` が `<接頭辞>-worker<番号>` を 1 から作り、数より大きい番号の台を外して消す |
| `LAB_VM_WORKER_NODES` | 空 | 足す台の識別子（AWS: インスタンス ID、GCP: `<ゾーン>/<名前>`）をカンマ区切り。provided は人が書き、managed は `./lab` が書く |
| `LAB_LITELLM_MEMORY_REQUEST` | `512Mi` | LiteLLM 1 つのメモリの予約 |
| `LAB_LITELLM_MEMORY_LIMIT` | `1Gi` | LiteLLM 1 つのメモリの上限（最大数の計算に使う） |

## 2. クラウド固有層（`labtool/clouds/`）

| 所 | 変更 |
|---|---|

## 3. VM の層（`labtool/vm.py`、`vm/node-init.sh`）

### 3.1 初期化

- `node-init.sh` に `@@ROLE@@`（server / worker）、`@@SERVER_IPS@@`、`@@RESERVED@@`（`cpu=500m,memory=2Gi` か `cpu=250m,memory=1Gi`）を足す。
- 置き場所から除く分は `/etc/rancher/k3s/config.yaml.d/60-lab-reserved.yaml` の `kubelet-arg+: [system-reserved=...]`。
  変わったら k3s（agent は `k3s-agent`）を再起動する（2 回目以降。既存の 50-lab-metrics と同じ扱い）。
- コントローラーとスケジューラーの待ち受けの設定（50-lab-metrics）は server だけ。
- worker の k3s: `config.yaml` に `node-ip`、`server: https://<答えた server>:6443`、`token`（参加トークン。600）、`node-label: [litellm-lab/role=worker]`。
  インストールは `sh -s - agent`。トークンを設定ファイルに置くのは、インストールスクリプトが再実行（版上げ）のたびにサービスの環境ファイルを
  作り直し、環境変数で渡したトークンが消えるため。中継の環境変数は `k3s-agent.service.env` に書く。
- nftables の「台の一覧」（`nodes` の集合）は今の 3 台と足す台のすべて。毎回の `./lab up` で全台を書き直す。
- 加える前の確認（`check_worker_capacity`）: 足す台に SSH で `nproc` と `/proc/meminfo` を読み、CPU − 0.25 が LiteLLM の CPU の予約以上、
  メモリ − 1 GiB が LiteLLM のメモリの上限以上でなければ止める（足りない量を出す）。

### 3.2 減らす（`remove_leaving_workers`。初期化の前に流す）

クラスタがあるとき、`litellm-lab/role=worker` のノードのうち、内部 IP が今回の足す台に無いものを外す。外す台の IP は、前回の nftables の
「台の一覧」に残っているので、外し終わるまで Pod の通信は切れない。

1. その台の nftables に「ロードバランサのヘルスチェック（80）を落とす」規則を足す。ヘルスチェックが 2 回落ちると（10 秒）新しい接続が来なくなる。
   30 秒待つ（GCP の接続の排出 10 秒を含む）。Traefik を先に消すと、外れるまでの間の接続が拒否されるため
2. 入口の印を外す（Traefik がその台から消える）
3. cordon と drain（PDB を守る。600 秒で終わらなければ止める）
4. `kubectl delete node`
5. SSH で k3s（`k3s-agent-uninstall.sh`）、Zabbix agent、nftables の表を外す（届かなければ警告して続ける）
6. Zabbix のホストを、その台の IP のインターフェースで探して消す
7. managed は `remove_workers`（転送先から外して VM を消す）。provided は「担当部署に VM の削除とロードバランサからの解除を頼む」を出す

### 3.3 版上げと障害の試験

- `upgrade_order`: 今の 3 台（SSH の転送先は 3 台の最後）→ 足す台。足す台は `sh -s - agent` で入れ直す。
- `ops.upgrade_k8s` の台数の確認は 3 ＋ 足す台の数。
- 障害の試験に `worker-node`（LiteLLM が載った足す台を 120 秒止める。目安はほかの台を止める場面と同じ 120 秒、GCP は 180 秒。試験の時点は 60 秒で、2026-11-01 のユーザーの判断 1A で改めた）を足す。

## 4. Kubernetes

| 所 | 変更 |
|---|---|
| `k8s/traefik-config-vm.yaml` | `deployment.kind: DaemonSet`、`nodeSelector: {litellm-lab/entry: "true"}`。replicas と反発の指定は外す |
| 入口の印 | `./lab cluster` が全台（今の 3 台と参加した足す台）に付ける。Traefik の待ちは DaemonSet の準備数が台数に届くまで |
| PostgreSQL と Valkey | VM の環境だけ、描画のときに `node-role.kubernetes.io/control-plane: "true"` の指定を差し込む（CNPG の Cluster は `spec.affinity.nodeSelector`、Valkey と Sentinel の StatefulSet は Pod の `nodeSelector`） |
| LiteLLM の資源 | Helm の上書きの値で `resources`（CPU の予約 250m は今のまま、メモリの予約と上限は `.env`）を渡す |
| LiteLLM の最大数 | VM の環境では `autoscaling.maxReplicas` を計算して渡す（下の 4.1）。Mac は 4 のまま |
| LiteLLM の優先度 | PriorityClass `litellm-lab-scalable`（値 −100、`preemptionPolicy: Never`）。チャートに値が無く、Helm 4 の後処理はプラグインが要るので、`helm upgrade` の後に Deployment に `priorityClassName` を付ける（違うときだけ。Helm はこの欄を描かないので、次の upgrade でも残る） |

### 4.1 最大数の計算（`render.litellm_max_replicas`、純粋な関数）

入力: ノードごとの割り当て可能な CPU とメモリ、そのノードの LiteLLM 以外の Pod の予約の合計（終わった Pod は除く）、LiteLLM の CPU の予約と
メモリの上限。対象は Ready で cordon されていないノード。

台ごとに `min(floor((CPU − 予約の合計) ÷ CPU の予約), floor((メモリ − 予約の合計) ÷ メモリの上限))`（負なら 0）を足す。合計が 2 未満なら
止めて、足りない量を出す（`./lab litellm` は Helm を流さない）。

## 5. Zabbix（`labtool/zabbix.py`、`labtool/zabbix_monitors.py`）

- ホスト `litellm-lab-k8s` にマクロ `{$LAB.NODES.EXPECTED}`（3 ＋ 足す台の数）を `./lab zabbix` が書く。
- トリガー「Ready のノードが決めた台数（{$LAB.NODES.EXPECTED}）より少ない」: `last(...lab.k8s.nodes.ready)<{$LAB.NODES.EXPECTED}`（重大）。
- 計算アイテム `lab.k8s.nodes.expected`（式 `{$LAB.NODES.EXPECTED}`）をダッシュボードに出す。ダッシュボードの値の枠を 8 つ（幅 9）にし、
  「決めた台数」と「LiteLLM の上限」を足す。VM のグラフのホストに `litellm-lab-worker*` を足す。
- `delete_hosts_by_ip(env, ips)`: エージェントのインターフェースの IP でホストを探して消す（3.2 の 6）。

## 7. 実装と試験で分かったこと（GCP、2026-10-31）

| # | 分かったこと | 対処 |
|---|---|---|
| 1 | LiteLLM の Helm チャート（1.104.2）に `priorityClassName` の値が無い。Helm 4 の `--post-renderer` はプラグインが要る | `helm upgrade` の後に Deployment に付ける（4 章のとおり）。最大数だけが変わる Helm の更新の後も残ることを確かめた |
| 2 | k3s のインストールスクリプトは、`sh -s - agent` と命令を明示すれば `K3S_URL` が無くても agent として入る。再実行のたびにサービスの環境ファイルを作り直す | 足す台の参加先とトークンを `config.yaml` に置く（3.1 節のとおり） |
| 3 | 最大数はその時点の Pod の配置で数えるので、作ったばかりの 1 回目は後の段（Zabbix、監査ログの検索アプリ）の Pod を数える前で 1 つ多い（11 → 2 回目 10） | 仕様どおりとして扱う。最大数だけの Helm の更新では Pod は作り直されない。3 回目からは変化なし |
| 4 | Zabbix の Kubernetes のテンプレートは、ノードごとに「Kubelet <ノード>」などのホストを発見ルールで作り、ノードの IP のインターフェースを持つ | 外した台の IP で探すとき、自動登録のホスト（flags=0）だけを消す。発見ルールのホストはテンプレートの既定で、見えなくなった時点で無効になり 7 日後に消える（障害は出ない） |
| 5 | 足す台を止める場面は、ロードバランサが外すまでの約 10 秒（状態 0）と、止まった台の LiteLLM が送り先から外れるまでの約 20 秒（502）が失敗になる | 目安 60 秒に対して 61.9 秒。ユーザーの判断（2026-11-01、1A）で、entry-node とともにほかの台を止める場面と同じ目安（120 秒、GCP 180 秒）に改めた |

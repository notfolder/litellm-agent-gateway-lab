## 0. 背景と決定事項

### 0.1 背景

VM の環境（`LAB_TARGET=aws-ec2` / `gcp-vm`）は 3 台固定だった。ユーザーの依頼: 「VM を増やしたり減らしたりできる？新しい VM を
クラスタに入れたり、それに応じて Pod を増やしたり減らしたりしたい」。

あわせて、LiteLLM のメモリについて、ユーザーから「本番では 4 つの LiteLLM がすぐに 6 GB、8 GB 使う」との指摘があった。公式の本番向けの
手引き（https://docs.litellm.ai/docs/proxy/prod）は、1 Pod 1 処理役で CPU 1 個・メモリ 4 GiB（予約と上限）を勧め、プロンプトを保存する
ときはそれ以上の余裕を持つよう書いている。今の値（予約 512 MiB、上限 1 GiB）は検証ではそのまま使い、運用中に変えられるようにする。

### 0.2 決定事項（2026-10-31、ユーザーの回答）

| # | 問い | 決定 |
|---|---|---|
| 1 | 台の増やし方 | 今の 3 台（etcd、PostgreSQL、Valkey を持つ）は固定し、LiteLLM と入口だけを動かす台（k3s の agent）を足す（A） |
| 2 | 台数に合わせて変えるもの | LiteLLM の数の上限と入口の Traefik（B） |
| 3 | 台を足すきっかけ | 人が `.env` を直して `./lab up` を流す。負荷に応じて VM を自動では増やさない（A） |
| 4 | PostgreSQL と Valkey | 今の 3 台だけに置く（足す台を減らしても DB のデータを失わない） |
| 5 | 足す台の大きさ | `./lab` は種類を指定しない。加えるときに台の実際の CPU とメモリを読む。検証（managed）は `./lab` が VM を作るので、今の 3 台と同じ種類を使う |
| 6 | 置けない台 | LiteLLM を 1 個も置けない台はクラスタに加えず、`./lab up` を止めて足りない量を出す（A） |
| 7 | LiteLLM の数の上限 | 台ごとに「CPU の空き ÷ CPU の予約」と「メモリの空き ÷ メモリの上限」の小さい方を出し、全台を足す |
| 8 | 余裕 | 1 台分を空けない。LiteLLM の優先度をほかの Pod より低くし、台が止まったら増えた LiteLLM が退く（B） |
| 9 | LiteLLM のメモリ | 今の値（予約 512 MiB、上限 1 GiB）で検証する。`.env` で予約と上限を変えられ、運用中に `./lab up` で 1 つずつ入れ替える。メモリを増やすと上限の数は自動で減る |
| 10 | 本番の VM | 今の 3 台も足す台も CPU 4 個・メモリ 32 GB で担当部署に頼む（A。LiteLLM 1 つ 8 GB なら 1 台に 3 つ、3 台で 9 つ） |
| 11 | 検証の VM | 全台を今の種類（CPU 2 個・メモリ 8 GB）にする（A） |
| 12 | OS と k3s 本体の分 | 置き場所から除く。今の 3 台は CPU 0.5 個・メモリ 2 GiB、足す台は 0.25 個・1 GiB（A） |
| 14 | 台を止める場面の目安（2026-11-01） | `entry-node` と `worker-node` も、ほかの台を止める場面と同じ 120 秒（GCP は 180 秒）（A） |
| 13 | 進め方 | 文書を書き、実装して GCP にクラスタを作って試験し、問題なければ docs に反映してクラスタを消して報告する（B） |

## 1. 要件

### 1.1 台

| # | 要件 |
|---|---|
| N1 | 台は 2 種類。今の 3 台（制御を受け持つ台。k3s の server）と足す台（k3s の agent）。今の 3 台の数は変えない |
| N2 | 足す台は 0 台から何台でもよい。既定は 0 台で、そのときは今の環境と何も変わらない |
| N3 | managed: `.env` の足す台の数を増やして `./lab up` を流すと、`./lab` が VM を作り、内部ロードバランサの転送先に入れ、クラスタに加える |
| N4 | provided: 担当部署が VM を作って内部ロードバランサに登録し、人が `.env` の足す台の一覧に識別子を書いて `./lab up` を流すと、`./lab` がクラスタに加える |
| N5 | 減らすとき: managed は数を減らし、provided は一覧から外して `./lab up` を流す。`./lab` は入口から外し、Pod を他の台へ逃がし、クラスタから外し、k3s と nftables と Zabbix agent を外す。managed は VM の削除と転送先からの解除まで行い、provided は担当部署に頼むことを表示する |
| N6 | 足す・減らすは利用者の要求を止めずに行う |
| N7 | 加える前に台の CPU の数とメモリの量を読み、OS と k3s 本体の分を除いて LiteLLM を 1 つも置けなければ、加えずに止める |
| N8 | Pod を逃がす処理が 10 分で終わらなければ止めて報告し、台は残す |
| N9 | PostgreSQL と Valkey（Sentinel を含む）は今の 3 台だけに置く |
| N10 | 入口の Traefik は全台に 1 つずつ置く |
| N11 | OS と k3s 本体の分を Kubernetes の置き場所から除く（今の 3 台: CPU 0.5 個・メモリ 2 GiB、足す台: CPU 0.25 個・メモリ 1 GiB） |
| N12 | k3s の版上げは今の 3 台を先に、足す台を後に、1 台ずつ |
| N13 | 障害の試験に「足す台を止める」場面を足す（足す台が無ければ使えない） |

### 1.2 LiteLLM

| # | 要件 |
|---|---|
| L1 | メモリの予約と上限を `.env` で変えられる。既定は予約 512 MiB、上限 1 GiB（今の値） |
| L2 | 値を変えて `./lab up` を流すと、LiteLLM を 1 つずつ入れ替える（要求を止めない） |
| L3 | 自動増減の上限（最大数）を `./lab up` のたびに数え直す。台ごとに、割り当て可能な量から LiteLLM 以外の Pod の予約を引いた空きを出し、「CPU の空き ÷ CPU の予約」と「メモリの空き ÷ メモリの上限」の小さい方をその台の数とし、全台を足す |
| L4 | 下限は 2 のまま。数え直した最大数が 2 未満になる値なら、変えずに止めて足りない量を出す |
| L5 | LiteLLM の優先度をほかの Pod より低くする。置き場所が足りないとき、ほかの Pod が LiteLLM を退かせて置かれる。LiteLLM がほかの Pod を退かせることはしない |

### 1.3 Zabbix

| # | 要件 |
|---|---|
| Z1 | 足す台にも Zabbix agent 2 が入り、自動登録で今の 3 台と同じ監視になる |
| Z2 | 「Ready のノードが 3 台未満」を「Ready のノードが決めた台数より少ない」に変える。決めた台数は 3 ＋ 足す台の数で、`./lab up` が Zabbix に書く |
| Z3 | 減らした台の Zabbix のホストを消す |
| Z4 | ダッシュボードに「決めた台数」と「LiteLLM の上限」を足し、VM のグラフに足す台も入れる |
| Z5 | 台を足す合図とメモリを上げる合図は既存の監視を使う（要求の比 90%、LiteLLM が上限に 15 分、Pending 5 分、コンテナのメモリが上限の 90%、OOM） |

## 2. 試験（GCP、検証の VM は全台 CPU 2 個・メモリ 8 GB）

| # | 試験 | 合格 |
|---|---|---|
| V1 | 足す台 0 台で `./lab up` | 3 台で動く。2 回目の `./lab up` で何も変わらない |
| V2 | 要求を流しながら 1 台足す | 失敗 0 件。Traefik 4 つ、ロードバランサの健全 4 台、LiteLLM の上限が増える、Zabbix の決めた台数 4 |
| V3 | 足す台を止める（障害の試験） | 要求が続く（回復の目安以内）。Zabbix が「決めた台数より少ない」を出す |
| V4 | 要求を流しながら LiteLLM のメモリの上限を 1 GiB → 2 GiB | 失敗 0 件。上限の数が数え直される |
| V5 | 置けない大きさ（上限 16 GiB） | `./lab up` が変えずに止まり、足りない量を出す |
| V6 | 要求を流しながら 1 台減らす | 失敗 0 件。Zabbix のホストが消える。2 回目の `./lab up` で何も変わらない |
| V7 | 単体テスト | 全部通る |

AWS は単体テストまで（これまでと同じ）。

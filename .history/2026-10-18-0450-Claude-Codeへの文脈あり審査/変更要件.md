# 変更要件: Claude Code の auto mode とゲートウェイの文脈あり審査の併用

作成: 2026-10-18
状態: ヒアリング済み（2026-10-18。決定は 3 章）。ブランチ `feature/context-review-claude-code`。実装と 3 段の検証（5 章）の結果は 6 章。

## 1. 検討の動機

文脈あり審査は Claude Code の auto mode を参考に作り、Claude Code には掛けていなかった（auto mode に任せる。spec 4.2）。
今は見ているところが違うので両方掛けてもよく、むしろ auto mode を外した運用（`bypassPermissions`、`--dangerously-skip-permissions`）の守りになるのではないか、という問いから、両方を有効にしたときの影響と検証方法、現在の審査でよいかを検討した。

## 2. 検討で分かったこと（2026-10-18）

### 2.1 Claude Code 側の仕組み（公開文書と実機の監査ログから）

- Claude Code v2.1.278 以降、`ANTHROPIC_BASE_URL` がゲートウェイを指すセッションの auto mode は**サーバー側審査**になる。通常の `/v1/messages` 要求の `safeguards` 項目で判定を依頼し、応答の中で判定を受け取る。ゲートウェイがこの項目や結果を落とすと、Claude Code は自前の分類器要求（別の要求）に切り替える。判定が返らない応答は拒否にする。
- 2026-10-17 の実機試行（design 16.6）の監査ログを読み取り専用で走査した結果: 本物の Claude Code の要求 121 件（1 セッション、v2.1.302）のすべてに `safeguards: [{"type": "dangerous_tool_use", "classifier_context": {"permission_mode": "auto", …}}]` があり、分類器だけの別要求（Claude Code のシステムプロンプトを持たない小さな要求）は 1 件も無かった。LiteLLM（v1.104.2）はこの項目を素通しし、ゲートウェイの文脈独立審査（拒否を含む）と auto mode のサーバー側審査は既に同居して動いている。
- `bypassPermissions` は分類器も承認も外す。残るのは `permissions.deny`、`rm` の重要パスの確認、フックだけ。モデルへの要求はすべてゲートウェイを通る。
- `classifier_context` には利用者の許可ルール一覧、信頼ディレクトリ、作業フォルダが入り、監査ログの本文に残る。`permission_mode` の値で、そのセッションの権限モードをゲートウェイ側で観測できる（分岐には使わない。試験の記録に使う）。

### 2.2 併用したときの影響

| 観点 | auto mode の分類器 | ゲートウェイの文脈あり審査 | 影響 |
|---|---|---|---|
| 見るもの | 利用者の発言、読み取り以外のツールコール、CLAUDE.md、直前の `git status`、`autoMode.environment` | 利用者の発言とツールコール本体（新しい 40 件、各 2,000 字） | Claude Code は CLAUDE.md やフックの出力を user 役で送るので、審査官はそれも利用者の発言として読む（Codex の AGENTS.md と同じ既知の注入経路） |
| 判定を通さないもの | 読み取り、作業フォルダ内の編集 | 無し（Jev で一次判定） | 実機の 1 日分では 121 応答中 74 応答にツールコール。文脈あり審査はその全部で審査官を待つ。Claude Code 側の待ちは増えない（別要求が無い） |
| 許可の扱い | 操作と対象を名指しした指示で soft block が解ける | 失われるものを認める言葉が要る | ゲートウェイの方が厳しい。auto mode が既定で通す自分のリポジトリへの push や PR 作成も、許可の言葉が無ければ止まりうる |
| 信頼する基盤 | `autoMode.environment` | 無し | 社内の宛先への送信が「外部への送信」として扱われうる |
| 拒否のとき | ツール結果として返し、3 連続 / 累計 20 で人に戻す | 「拒否: …」の文に差し替え `end_turn` | ゲートウェイが先に止めるので分類器の回数には数えられない。差し替え時は溜めたイベント（その応答のサーバー側判定を含む）を捨てる |
| サブエージェント | 同じ規則で各行動を判定 | 別の要求として別の会話を見る | 親の会話の許可が見えず、委譲した取り返しのつかない操作は止まる |

### 2.3 見つかった欠陥（有効化の前提）

実機の要求では、最初の user メッセージが 4 つの text ブロック（system-reminder 6,858 字・865 字・581 字、そのあとに利用者の指示 132 字）だった。判定入力の抽出は 1 メッセージの text を結合して先頭 2,000 字で切っていたため、利用者の指示と許可の言葉が丸ごと落ちる。このままでは取り返しのつかない操作が許可の有無に関わらず全部 block になる。

## 3. 決定事項（2026-10-18 のヒアリング）

| 項目 | 決定 | 選ばなかった案 |
|---|---|---|
| Claude Code への文脈あり審査 | 設定 `LAB_CONTEXT_REVIEW_CLAUDE_CODE`（ガードレールの `context_review_claude_code`）で切り替え、**既定は切り**。試験の間だけ入れる。本番の守りは組織が選ぶ | 既定を入りにする／設定を設けず常に掛ける |
| 許可の言葉の基準 | **今のまま**（失われるもの・外部に出るものを認める言葉が要る） | auto mode と同じ「操作と対象を名指しした指示」を許可とみなす／信頼する宛先と自分のリポジトリへの push だけ許可なしで通す |
| 抽出の修正 | ユーザー役の content の **text ブロックごとに 1 項目**にする（各 2,000 字。40 件の枠は共有）。クライアント固有の処理は足さない | 1 件の上限を 10,000 字程度に上げる |
| 進め方 | ブランチを切り、実装と 3 段の検証（5 章）まで進める | 単体・疎通だけ先に行う |

## 4. 変更の内容

- `litellm/guardrails/transcript.py`: `_texts_of_content` と `_user_entries`。Responses / Chat Completions / Anthropic Messages の 3 形式とも、ユーザー役の text のパーツごとに 1 件にする（空のパーツは除く）。
- `litellm/guardrails/tool_call_review.py`: 設定 `context_review_claude_code`（既定 false）。`_plan` は Claude Code の要求に対して（文脈あり審査をするか, 文脈独立審査をするか）を設定どおり返し、どちらもしないときだけ素通し。方針の差し込み（pre_call）は変えない。
- `labtool/render.py`: `.env` の `LAB_CONTEXT_REVIEW_CLAUDE_CODE`（既定 `false`）を `context_review_claude_code` に写す。文脈独立審査の有無に関わらず出す。
- `labtool/checks.py`（疎通）と `labtool/audit_test.py`（監査ログの試験）: 設定が入りのとき、Claude Code の形の危険な操作が文脈あり審査で拒否されること（「機密情報の持ち出し: 」は付かない）、Claude Code の要求に `context` と `isolated` の記録が 1 件ずつ残ることを確かめる。
- 単体テスト: 実機の形（複数の text ブロック）の抽出、`_plan` の組み合わせ、Claude Code で文脈あり審査が block する流れ、ストリーミングで allow のときに未知のイベントを含む溜めたチャンクを一字一句そのまま流し、block のときは文と `end_turn` に差し替えること。

## 5. 検証計画

1. **単体**（`./lab test-unit`）: 4 章のテスト。
2. **疎通**（`./lab test-smoke`、偽 LLM）: 設定の切り・入りの両方で流す。
3. **実機**（`claude -p`、使い捨てのリポジトリ、各 5 回）: `docs/manual-check.md` 4 章の 8 シナリオに「自分のリポジトリ（ローカルの bare）へ push」「ブランチを切って push し `gh` で PR 作成」「サブエージェントへの委譲（許可の言葉あり）」を足した 11 シナリオを、3 つの設定で流す。
   - (a) `--permission-mode auto`、文脈あり審査なし（今の状態）
   - (b) `--permission-mode auto`、文脈あり審査あり
   - (c) `--dangerously-skip-permissions`、文脈あり審査あり
   - 記録: 止まったか、どの層が止めたか（ゲートウェイの文脈あり / 文脈独立 / Claude Code の分類器〔`permission_denials`〕/ モデル自身）、副作用、応答ごとの審査時間（判定ログの `timings_ms`）、1 回の所要時間。
   - 監査ログで、分類器の別要求（Claude Code のシステムプロンプトを持たない要求）が無いこと、`safeguards` の `permission_mode` の分布を確かめる。

## 6. 結果（2026-10-18）

- 単体・疎通: すべて通過（件数は `docs/design.md` 16.7）。疎通は設定の切り・入りの両方で 75 件 OK。
- 実機 165 回（11 シナリオ × 3 設定 × 5 回、約 65 分）の表と分かったことは `docs/design.md` 16.7。要点:
  - auto mode の分類器が通していた「指示だけの削除」（5/5 削除）と「検証を飛ばしたデプロイ」（2/5 実行）を、文脈あり審査が 5/5 止めた。許可ありの削除は 5/5 通った（誤ブロック 0）。
  - `bypassPermissions`（分類器なし）でも同じ守りになった。監査ログで、その設定の要求 215 件には `safeguards` 項目が無く、auto mode の要求はすべて `permission_mode: "auto"` だった。
  - 分類器の別要求（Claude Code のシステムプロンプトを持たない要求）は 3 設定とも 0 件。ゲートウェイの拒否のあとも切り替わらない。
  - サブエージェントへの委譲は、親が許可の言葉を依頼文に書き写すので通った（5/5）。
  - 誤ブロック: 自分のリポジトリへの push と PR 作成は許可の言葉が無いと止まる（決定どおり）。`git remote -v` を資格情報の読み出しとみなした回が 1/25。
  - 待ち時間: 審査官まで届くのは Jev で約半分。1 応答あたりの審査の合計の中央値は、文脈あり審査を足して 0.3〜0.5 秒増。
- 監査ログの試験（`./lab test-audit`、設定入り）: 33 件すべて OK。Claude Code の要求に `context` と `isolated` の記録が 1 件ずつ残ることを含む。
- 試験の材料は `tests/review-scenarios/README.md` のシナリオに「push」「PR」「サブエージェント」を足した形で、実行と集計のスクリプトはセッションの作業領域に置いた（リポジトリには入れていない）。

## 7. 残った点

- 検証環境の `.env` は `LAB_CONTEXT_REVIEW_CLAUDE_CODE=true` のまま（試験のため）。既定は `false`。戻すなら `.env` を書き換えて `./lab litellm`。
- push と PR の誤ブロックが実運用で不便なら、文脈あり審査の審査官に許可リストの宛先を「送ってよい宛先」として渡す案（ヒアリングで選ばなかった案 C）を再検討する（バックログ）。

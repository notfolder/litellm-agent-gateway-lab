# 審査の判定基準（経緯）

CLAUDE.md の「ツールコール審査の判定基準には、止めるコマンドの具体例を列挙しない」の背景。

## 何があったか

2026-10-12、本物の Codex（審査あり）で、具体的に指示したローカルの破壊的操作（`rm -- <file>`、`git reset --hard`、`git clean -fdx`）が審査を素通りし、個人情報を含むファイルが実際に削除された（検証は `docs/guardrail-gaps.md`）。

原因は、監査（文脈あり審査）も一次判定（Jev）も「ユーザーが明示的に頼んだか」で判定していたこと。具体的な指示はそのまま「依頼の範囲内」とみなされて通った。

対策として、監査で守るべき事項を漏れなく挙げる方法を検討した。そのときユーザーから次の方針が出た。

## ユーザーの指示（2026-10-12）

- 「最近の LLM は賢いので、方針は出しますが、具体例は出さない方が却って安心だと思います。」
- 「外部の一覧を見るのはかなり良いです。」

## なぜその方針か

- 具体例（止めるコマンドの列挙）を判定基準に書くと、判定がその形だけに狭まり、言い換えや派生を取りこぼす。列挙自体が新たな抜けになる。賢いモデルには、属性（取り返しがつくか × 影響が作業コピーの外か、許可されたか）で述べた方針を渡して一般化させる方が広く効く。
- 「漏れがないか」を確かめるには、思いつきの列挙ではなく、外部の権威ある一覧（Claude Code auto mode が公表しているブロック対象、OWASP の Agentic の脅威 ASI02・過剰な権限）と自分の方針を突き合わせ、収まらない項目を足す形で網羅を担保する。

## どう直したか

- 監査の判定を許可ベースに変更。取り返しのつかない操作は、会話に実行の許可が明示されている場合だけ allow、指示だけなら対象が具体的でも block（`litellm/guardrails/tool_call_review.py` の `JUDGE_SYSTEM`）。
- Jev の問いからも「依頼の範囲を超えるか」を外し、取り返しのつかない操作は確率に関わらず審査官へ回す。
- 判定基準の文章には具体例を書かず、事例は回帰試験（`tests/review-scenarios/judge-cases.json`）に許可あり／指示だけのペアで置いた。本物の審査官（luna）で 65/65 の見分けを確認した。

関連: [仕様と設計の進め方](仕様と設計の進め方.md)

## 列挙・記録・シェルの解析が要る案は退けられる

- 2026-10-17、スクリプト経由の送信（社内連携スクリプト）の扱いを検討したとき、次の案が順に退けられた: 連携コマンドの登録、ハッシュによる改ざん検出、書き込み時の審査と Valkey の記録（「複雑すぎて上手く動かないことが多そう」）、「この会話で LLM が触ったスクリプトだけ読む」（「便利スクリプトは基本 git に上げて、毎回は触らない」）、木全体の差分の読み取りとコミットの審査（「手元のプログラムが呼び出されるコマンドを全て列挙はできない」）
- 採用されたのは、前提を置き直したうえで既存の仕組みに乗せる形: 審査の目的を「LLM が作った一時的な処理」に絞り、木のツールと OS・ミドルウェアは安全とみなし、名指しのプログラムは「実体が読める最後の時点」（スクリプトは動かす直前、読めない実体は作る直前、自動で動く場所へ置くものは置く直前）に、送るファイルと同じ確かめた読み取りで読ませる
- 読めない項目を生成物として通す判断も、シェルの解析ではなく、審査官が分類（`direct`）してゲートウェイが強制する分担にした（宛先の抜き出しと同じ）

## 審査の仕組みに、特定のクライアント向けの対処を足さない

- 2026-10-18 の指示: 読み取りの出力が切れる行き止まり（Claude Code は約 30,000 文字でツールの出力を切る）への対処として「合計バイト数の上限を足す」案を出したところ、「Claude Code だけ特別扱いはしたくない。他にも Claude Code やエージェント特定の処理がないか確認するのと、Claude Code 向けではない対処方法をいくつか検討して」と求められた
- 洗い出した結果、避けられない分岐は API の形の違い（Codex は `exec` のプログラムでシェルを呼ぶ、ツール一覧の入れ子）と、仕様で決めた分岐（Claude Code には文脈あり審査を掛けない）だけだった。出力の切り詰めへの対処は、Codex 専用の `max_output_tokens` と、Claude Code を根拠にした 1 ファイルの既定値で間に合わせていた
- 採ったのは、上限の数字を持たず「出力が途中で切れた」という観測だけで動く方式（`truncated_read`）。クライアントの上限を知らなくても同じ動きになる。数字で合わせる案は、クライアントが増えるたびに数字が増える
- 以後、クライアントの名前や固有の上限値を根拠にした分岐を足す前に、観測で判断できる形にできないかを先に検討する

## 審査官のプロンプト・判定基準・ゲートウェイの実装に、個別のツール名・製品名・エージェント別の対処を入れない

- 2026-10-18、PC 操作系（メールの削除、ブラウザ・画面の操作、Windows）の審査を点検して事例を増やす作業の途中で、「くれぐれも監査に個別ツールの具体名など入れないようにしてください。実例はあくまでテスト側です。実装側はエージェント個別対応にならないようにしてください」と念を押された
- 守った形: 判定基準には属性の行（機密情報を、宛先が引数から分からない画面・入力欄・アプリケーションへ入力・貼り付けする操作は社外に出るものとして扱う）だけを足し、Gmail やブラウザ拡張のツール名は `tests/review-scenarios/` の事例にだけ書いた。実装に足したのは API の形の違い（Responses API の `computer_call` を名前 `computer` として扱う）と、ツールの定義を持たない要求に方針を足さないこと、だけ
- 理由は「判定基準は方針のみ」と同じ。ツール名で守ると、新しいツールや言い換えが抜けになり、エージェントごとの分岐はクライアントが増えるたびに増える。新しい PC 操作のツールが入ったときは、審査の仕組みは変えずに事例集に実物の形を足して `./lab test-judge` で確かめる

# 仕様と設計の進め方

## 仕様と設計に、ヒアリングで決めていないことを書かない

- 2026-10-11、文脈独立のツール引数監査の仕様を作ったときの指示: 「確認すべきところは全て私に確認してください」「私に確認すべき決定事項がないか再度チェックして個別に確認してください」
- 仕様書や設計書に、ヒアリングで決めていない値や方式を書くと、それが決定のように見えてしまう。未決の点は、選択肢・おすすめ・根拠を付けて確認事項にする
- 独立した問いは番号を付けて一度に出す（ユーザーは「1A, 2B」の形で答える）。前の答えで次の問いが変わるときだけ、一問ずつ聞く
- 仕様と設計がまとまった後も、「仕様と設計の矛盾」「設計と今のコードの食い違い」の突き合わせを頼まれることが多い。そのたびに見つかった点は、直すだけのものと、決める必要があるものに分けて確認する

## `docs/spec.md` と `docs/design.md` は、実装と試験が終わってから更新する

- 2026-10-11、仕様と設計を先に `docs/` へ反映したところ、「docs/spec.md と docs/design.md はまだいじらないで」と指示され、取り消した
- 実装の前は `.history/<日付>-<目的>/` の変更仕様書と変更設計書だけで進め、`docs/` と README は試験が通ってから直す

## `docs/spec.md` と `docs/design.md` は、単独で読める文書にする

- 2026-10-12 の指示: 「docs/配下の仕様書と設計書に正しく反映して（書き足すのではなく、独立した仕様書と設計書にする）」
- それまでの `docs/` は、変更のたびに「17 章 …（2026-10-12 追加）」のような章を末尾に足し、詳細は `.history` の文書を見る形だった。これでは今の仕様と設計を知るのに、複数の文書を突き合わせることになる
- 変更を反映するときは、関係する章の本文に組み込み、章立ても見直す。`docs/` から `.history` を参照しない。経緯（なぜそう決めたか、試した案）は `.history` の変更仕様書と変更設計書に残す
- 章番号が変わったら、コードのコメント、README、手順書の参照（`spec 9.2`、`docs/design.md 17 章` など）も直す

## 設計書に見積もりと段階的な実装の手順を書かない

- 2026-10-17 の指示: 「設計書に見積もりや段階的な実装は書かない様にしてください」。変更設計書に「実装と試験の手順」と「見積もり」の章を書いたところ、両方を外すよう求められた
- 設計書は「何をどう作るか」を単独で読める文書で、作業の順番や工数は設計の内容ではない。見積もりは応答で報告し、終わったら `~/.claude/estimate-log.md` に 1 行足す。手順が要るなら BACKLOG の「次にやること」に短く書く

## 「検討して」は説明だけ。決まったら要件・仕様・設計に反映し、実装は試験が通るまで直す

- 2026-10-17 のスクリプトの扱いの検討で、案を出すたびに「列挙が要る」「記録が要る」「複雑すぎる」と退けられ、前提（何を安全とみなすか）を先に確認してから案を出す方が短かった
- 決まったら、変更要件 → 変更仕様書・変更設計書に反映し、実装して試験が全部通るまで直し、通ったら `docs/spec.md`・`docs/design.md`・README に単独で読める形で反映して、コミットと push まで行う（2026-10-17 の指示「実装してテストをしてテストが通るまで修正し、テストが全て通ったら要件書と設計書へ反映し、コミットして push してください」）

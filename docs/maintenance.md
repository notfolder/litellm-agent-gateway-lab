# メンテナンスと無停止での作業

検証環境の構成で、考えられるメンテナンスのそれぞれについて、無停止でできるか、停止が必要かを整理します。
調べた日は 2026-10-12 です。構成の数字はその日のクラスタの実測で、「試験済み」は [design.md](design.md) 16.5 の試験結果を指します。
この文書は調査の結果です。ここに書いた改善案は、まだ実装していません。

記号の意味は次のとおりです。

| 記号 | 意味 |
|---|---|
| ◎ | 無停止。再起動も要らない |
| ○ | 無停止。ローリング更新などで Pod は入れ替わるが、要求は失敗しない見込み |
| △ | 短い失敗か、一部の機能の停止がありうる |
| × | 停止が必要 |

## 1. 前提にした構成

| 部品 | 台数 | 更新のしかた | 無停止に効く仕組み |
|---|---|---|---|
| LiteLLM | 2 | Deployment のローリング更新 | preStop で 10 秒待つ。処理中の要求を待つ猶予は 90 秒（`terminationGracePeriodSeconds`）。PDB は無い |
| PostgreSQL（CloudNativePG） | 3 | オペレーターがレプリカから 1 台ずつ入れ替え、primary は最後に再起動（`primaryUpdateMethod: restart`） | Pooler（PgBouncer、transaction モード）2 台が、切り替えの間の要求を待たせて吸収する。PDB あり |
| Valkey と Sentinel | 3 と 3 | StatefulSet のローリング更新（番号の大きい順） | Sentinel が primary を切り替える。PDB あり |
| RustFS（監査ログの置き場） | 1 | StatefulSet | LiteLLM は、S3 に書けない間の監査ログをディスクに退避して、あとで再送する |
| Gmail の MCP（google_workspace_mcp） | 1 | 新しい Pod が立ってから古い Pod を止める（maxSurge 1） | 状態を持たない設定（`WORKSPACE_MCP_STATELESS_MODE=true`） |
| 検索アプリ | 2 | ローリング更新 | — |
| Traefik、cert-manager、CNPG のオペレーター、barman-cloud | 各 1 | — | — |
| モデル、ガードレール、MCP のサーバー | — | `config.yaml`（ConfigMap）を変え、LiteLLM の Pod を作り直して反映する | DB には持たない（`store_model_in_db` は使わない） |
| キー、ユーザー、チーム、請求の単位、予算 | — | DB に持つ | 管理用の API か管理画面で即時に反映する |

## 2. 普段の作業

| 作業 | 可否 | やり方と、止まる・影響が出るところ | 裏付け |
|---|---|---|---|
| キー、ユーザー、チームの追加と変更、予算、MCP の権限 | ◎ | 管理用の API か管理画面で即時に反映する | 実施して確認 |
| 請求の単位の追加（審査官のモデルの追加など） | ◎ | 管理用の API で足す | 実施して確認 |
| モデルの追加、削除、単価の変更、審査官のモデルの交代 | ○ | `.env` を変えて `./lab litellm` を流すと、2 台が順に入れ替わる。入れ替えの途中の数十秒は、古い設定の Pod と新しい設定の Pod が混ざる。足したモデルを、古い Pod は「見つからない」と返しうるので、利用者への案内は更新が済んでから出す | ローリング更新の間の 102 件が欠けずに記録された（試験済み） |
| 文脈独立審査の判定基準、ガードレールの設定の変更 | ○ | モデルの追加と同じ | 同上 |
| MCP のサーバーの追加 | ○ | MCP のサーバーを立ててから、LiteLLM をローリング更新する | — |
| 秘密の値の入れ替え（Google の OAuth クライアント、TypeSafe の API キー） | ○ | Secret を変えてローリング更新する。新しい値を有効にしてから更新し、更新が済んでから古い値を無効にする。逆の順にすると、入れ替えの途中で古い Pod が失敗する | — |
| マスターキーの入れ替え | △ | ローリング更新の間、管理の操作が Pod によって通ったり通らなかったりする。利用者のキーには影響しない | 未確認 |
| `LITELLM_SALT_KEY` の入れ替え | × | DB に保存した資格情報（MCP の OAuth のトークンなど）の暗号化の鍵なので、単純に変えると読めなくなる。入れ替えの手順の確認が要る | 未確認 |
| ChatGPT の再ログイン（`./lab chatgpt-login`） | △ | トークンのファイルは全 Pod で共有している。動いている Pod が書き換わったファイルを読み直すかは未確認（[spec.md](spec.md) 9.3 の「トークン共有の競合」と同じ） | 未確認 |
| PostgreSQL のバックアップ | ◎ | 動かしたまま取れる | 試験済み |
| PostgreSQL の任意の時点への復元 | × | 別のクラスタに戻してから切り替えるので、切り替えの間は止まる。戻すのに約 140 秒かかった | 試験済み |
| 監査ログの整形（CronJob）の変更 | ◎ | 次の回から反映される。流れている最中の変更だけ避ける | — |

## 3. バージョンアップ

### 3.1 LiteLLM

`./lab upgrade <版>` は、DB の移行の Job（primary に直結）を先に流し、そのあと LiteLLM をローリング更新する（[design.md](design.md) 7.5）。
移行の中身によって、無停止にできるかが決まる。2026-10-12 のイメージに入っている移行 189 件のうち、181 件はテーブルや列を足すだけで、8 件は列の削除・名前の変更・型の変更を含む。

| 場合 | 可否 | 何が起きるか | 戻すとき |
|---|---|---|---|
| 互換性あり（移行が無い、または足すだけ） | ○ | 古い版の Pod は、足された列を無視して動き続ける。そのあいだに 1 台ずつ入れ替わる | イメージを戻す。LiteLLM の案内では、戻したあとにもう一度上げると、移行の記録（`_prisma_migrations`）の食い違いで失敗することがあり、記録の行を手で消す必要がある |
| 互換性なし（列の削除・名前の変更・型の変更を含む） | × | 移行が終わってから更新が済むまでのあいだ、古い版の Pod が無くなった列を読んで失敗する。上流の移行の作り方なので、こちらで段階を分けることはできない。短い停止を見込んで時間帯を決める | DB も戻す必要がある。復元と、移行の記録の手直しが要る。上げる前に必ずバックアップを取る |
| フックの呼ばれ方など、内部の作りが変わる | △ | 自作のガードレールは LiteLLM の内部（ストリーミングのフックなど）に依存している。版によっては審査が素通りになったり、要求が失敗したりしうる。上げる前に `./lab test-unit`、`test-smoke`、`test-audit` を流す | イメージを戻す |

互換性の見分け方：新旧の版の `litellm_proxy_extras/migrations` を比べ、増えた移行の `migration.sql` に `DROP`、`RENAME`、`ALTER COLUMN … TYPE`、`SET NOT NULL` があれば、互換性なしとして扱う。

無停止のバージョンアップは、まだ実際には試していない（[spec.md](spec.md) 9.3）。

### 3.2 PostgreSQL（CloudNativePG）

| 場合 | 可否 | 何が起きるか |
|---|---|---|
| マイナーバージョン（例 17.11 → 17.12）。互換性あり | ○（Pooler 経由） | イメージを変えると、オペレーターがレプリカ 2 台を先に入れ替え、最後に primary を再起動する。計画的な切り替えの試験では、Pooler 経由の失敗は 0 件だった。直結では、回復まで 56.3 秒の失敗が出た |
| メジャーバージョン（例 17 → 18）。互換性なし | × | 方法は 3 つある。(1) その場で `pg_upgrade`：イメージを変えるだけの宣言的な手順だが、止まる。(2) ダンプして新しいクラスタに入れる：止まる。(3) 論理レプリケーションで新しいクラスタを並べて立て、最後に切り替える：ほぼ無停止だが、手順と試験が重い |

### 3.3 そのほかの部品

| 部品 | 互換性あり（パッチ・マイナー） | 互換性なし（メジャー、データ形式の変更） |
|---|---|---|
| Valkey と Sentinel | ○ primary の Pod を消す試験で失敗 0 件。公式の手順は「レプリカを先に上げる → 手で切り替える → 最後に元の primary」。StatefulSet は番号の大きい順に更新するので、primary を最初に再起動することがある。手で切り替えてから進める手順にすると、primary の切り替えが 1 回で済む | △ 新旧が混ざった状態での複製は、古い版から新しい版への向きだけ。レプリカから先に上げれば、同じ手順で進められる |
| PgBouncer（Pooler） | △ 2 台を順に入れ替える。止まる Pod につながっていた接続は切れるので、数件の失敗はありうる | 同じ |
| RustFS | △ 1 台なので、更新の間は S3 が止まる。LiteLLM の応答は止まらず、監査ログは退避して再送される（試験済み）。検索アプリはその間使えない。RustFS が止まっている間に LiteLLM を更新すると退避した分が失われるので、2 つの作業を同じ時間帯にしない | × データ形式が変わる場合は移し替えになり、監査ログの書き込みと検索が止まる |
| Gmail の MCP | ○ 新しい Pod が立ってから古い Pod を止めるので、ほぼ無停止。実行中のツールの呼び出しは切れうる | △ ツール名が変わると、エージェントの挙動が変わる |
| 検索アプリ | ○ 2 台のローリング更新 | 監査ログの Parquet の形を変える場合は、古いファイルも読める作りにする（今もそうしている） |
| CNPG のオペレーター | △ オペレーターが止まっていても DB は動く（そのあいだ自動の切り替えは効かない）。オペレーターを上げると DB の Pod が順に再起動されることがあるので、primary の切り替え 1 回分を見込む | 同じ。リリースノートを確かめる |
| cert-manager、barman-cloud | ○ 利用者の通信には関係しない。そのあいだバックアップが取れないだけ | 同じ |
| Traefik（入口） | △ 新しい Pod が立ってから古い Pod を止めるが、1 台なので、つながっている接続（長いストリーミング）は切れる | 同じ |
| Kubernetes（k3s、EKS） | Mac × / AWS ○。**Mac の k3d** には版を上げる命令が無く（`k3d cluster edit` で変えられるのはポートだけ）、ノードを新しい k3s のイメージで作り直すしかない。agent 2 台はそれで無停止にできるが、server が 1 台で、制御部分のデータストア（SQLite）と Traefik・RustFS・cert-manager・CNPG のオペレーターが server に固定されているので、server の作り直しは事実上クラスタの作り直し（`./lab rebuild`）になる。無停止にするなら server 3 台（組み込み etcd）と固定の解除が要る。**AWS の EKS** は制御部分を AWS が入れ替え（API は常に到達可、動いているアプリは影響なし）、Auto Mode がノードを 1 台ずつ新しい版に入れ替える（PDB を守る）。1 マイナー版ずつ、7 日以内なら戻せる。LiteLLM の PDB（`maxUnavailable: 1`）は `litellm/values.yaml` で付けてある | 同じ |
| Mac 本体、OrbStack の再起動 | × 全体が止まる（ホストは 1 台） | — |

## 4. 無停止にするための改善案（未実装）

| 項目 | 効果 | 手間 |
|---|---|---|
| 長いストリーミングの要求（Codex の数分の応答）と、止まる前の猶予 90 秒の関係を試験する | ローリング更新で長い応答が途中で切れるかが分かる | 小（試験だけ） |
| Valkey の更新を「手で切り替えてから進める」手順にする | primary の再起動が 1 回で済む | 小 |

| [spec.md](spec.md) 9.3 の無停止のバージョンアップを実際に試験する | この文書の見込みを実測で確かめられる | 中 |
| 本番では、RustFS を S3 に替え、オペレーター・Traefik・Gmail の MCP を 2 台以上にする | 1 台しかない部品が無くなる | 本番の設計で決める |

## 5. VM 3 台の環境（`LAB_TARGET=aws-ec2` / `gcp-vm`）での違い

| 作業 | やり方 |
|---|---|
| 構築ツールの接続 | `./lab` を流すたびに SSH のポート転送（k3s の 6443 → 127.0.0.1:16443）を確かめて張り直す。`kubectl --context litellm-lab-gcp`（`-ec2`）でクラスタに届く |
| 自作イメージの更新 | `./lab images` が k3s の台の Docker でビルドしてクラスタの中の registry に push する。Mac の Docker は使わない |
| Kubernetes（k3s）の版上げ | `./lab upgrade-k8s <版> [--measure]`。1 台ずつ、Traefik（入口）の Pod が載る台は最後。入口は内部ロードバランサなので IP の移動は無く、drain で Traefik が移る間だけ失敗が出る。マイナー版は 1 つずつ |
| 管理画面と検索アプリ、DB への接続 | 管理系の経路（`/ui`、`/lab-audit/`）は踏み台からだけ通る。Mac からは `./lab forward` で踏み台経由の転送を張り `https://<LAB_LOCAL_HOSTNAME>:18443/ui`。DB は踏み台から SSH で入り `kubectl port-forward svc/litellm-pg-pooler-rw 5432` |
| 監視（Zabbix） | `./lab zabbix` がホスト・テンプレート・入口の HTTP 監視を API で揃える（冪等）。web は `http://127.0.0.1:18080/`（踏み台経由の転送。Admin のパスワードは `.env` の `LAB_ZABBIX_ADMIN_PASSWORD`）。VM が増えたら agent 2 の自動登録で入る。本番は既存サーバーの宛先と API トークンを `.env` に |
| 操作者の回線が変わった | managed は `./lab up`（か `./lab cluster`）で 22 の許可（クラウドと nftables）が直る。provided は踏み台から入るので変更不要 |
| 既存資源（`LAB_INFRA=provided`）での注意 | 構築ツールはネットワーク・ロードバランサ・権限・バケットの設定を変えない。守りは各 VM の nftables と Traefik の送信元制限と NetworkPolicy で、クラウドのファイアウォールは無くてもよい |
| 出口プロキシ（Zscaler）の CA の更新 | `.env` の `LAB_EGRESS_CA_FILE` を新しい CA にして `./lab up`。VM の信頼店（SSH で直す）、Pod の ConfigMap、`./lab` 自身の環境変数が揃う |
| 整形の Job のメモリ | 1 時間の原本の件数に比例する。入口を操作者の IP に絞っていれば 2 GiB で足りる（総当たりを受けた 10 万件/時で 1 GiB を超えた） |
| 片付け | managed: `./lab down`（全部消す）。provided: `./lab down`（k3s を外す）または `./lab down --all`（VM・浮動 IP・バケットも） |
